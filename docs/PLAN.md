# 설계 배경과 근거

`CLAUDE.md`의 규칙들이 왜 그렇게 정해졌는지를 담은 문서.
규칙을 바꾸고 싶어질 때 여기를 먼저 읽을 것.

---

## 1. 이전 프로젝트의 실패

### 무엇이 있었나

한투 API + AWS EC2 + MySQL 기반 자동매매 시스템. 정량·기술적 지표로 후보를 거른 뒤
남은 종목의 데이터를 차트 이미지로 변환하고, Claude가 이미지를 분석해 신뢰도 점수를
매겨 문턱을 넘으면 매수하는 구조였다. 모의투자에서 약 10% 수익이 나왔다.

### 무엇이 문제였나

수익이 지속되지 않았고, **매수하면 안 되는 상황에서도 매수가 발생했다.**

구조적 원인은 스케줄러에 있었다. 15:35 장 마감 후부터 18~24시 매시 정각에,
pending 신호가 5개 미만이면 `pre_market_setup(is_retry=True)`를 재실행하는 로직이
있었다. 의도는 "분석이 덜 끝났으면 마저 하자"였지만, 실제 작동은 "5개를 채울 때까지
계속 돌린다"였다.

같은 후보를 반복해서 LLM에게 보여주면 언젠가는 통과한다. 문턱값을 낮춘 코드는 어디에도
없지만, **재시도 자체가 문턱을 낮추는 역할을 했다.**

### 왜 이게 치명적이었나

매일 매수가 강제되면 신호의 예측력을 측정할 수 없다. 어떤 매수가 "신호가 좋아서"이고
어떤 게 "할당량을 채워야 해서"인지 사후에 구분할 방법이 없기 때문이다.

그래서 "수익이 안 났다"와 "무리하게 샀다"는 별개 문제가 아니다.
**후자가 전자의 원인 진단을 불가능하게 만든 관계다.**

모의투자 10% 수익도 마찬가지로 해석 불가다. IC 같은 지표로 유의성을 확인하지 않았기
때문에, 몇 개 종목이 우연히 터진 결과일 가능성을 배제할 수 없다.

### 코드를 재사용하지 않는 이유

두 가지다. 하나는 위 결함이 스케줄링·재시도·상태 복원 로직 전반에 얽혀 있어서
부분 수정으로 걷어내기 어렵다는 것. 다른 하나는 그냥 다시 손대고 싶지 않다는 것이고,
이건 충분한 이유다. 사이드 프로젝트는 의욕이 연료다.

가져오는 것은 **워크플로우 지식**뿐이다. 휴장일 처리, 장 마감 후 분석 → 다음날 개장
매수 흐름, EC2 재기동 시 캐치업 같은 운영 노하우는 두 번째 구현에서 훨씬 빠르게 나온다.

## 2. 계층 설계의 근거

### 수집은 에이전트가 아니다

뉴스 크롤링, DART 조회, 시세 fetch는 전부 결정론적 ETL이다. 여기에 LLM을 붙이면
비용과 레이턴시만 늘고 재현성이 깨진다. LLM 호출은 판단이 필요한 지점에만 넣는다.

### 왜 강세/약세 토론 단계가 있나

LLM은 주어진 근거에 동조하는 편향이 강하다. 분석가들의 의견을 그대로 종합하면
긍정 방향으로 쏠린다. 반대 논거를 **명시적으로 생성하게 강제**해야 균형이 잡힌다.

### 에이전트 합의는 신뢰의 근거가 아니다

같은 base model 5개가 동의하는 것은 독립 표본 5개가 아니라 상관된 오류 1개다.
진짜 다양성은 모델이 아니라 **데이터 소스**에서 나온다. 차트만 보는 분석가와 공시만
보는 분석가가 다른 결론을 내는 건 의미가 있지만, 같은 뉴스를 두 번 읽히는 건 의미가 없다.

이것이 분석가를 데이터 소스 기준으로 나눈 이유다.

### 왜 리스크 게이트가 LLM이 아닌가

종목당 최대 비중, 섹터 집중도, 일일 최대 손실, 총 노출은 "판단"의 영역이 아니라
넘으면 무조건 거부하는 하드 룰이다. LLM에게는 거부권만 주고 승인권은 주지 않는다.

### 비용 구조

KOSPI200 전체에 분석가 4개를 돌리면 하루 800회 호출이다. 정량 필터로 후보를
10~20개로 줄인 뒤에 LLM을 투입하는 순서를 유지한다.

종목당 독립 호출(비교 금지) 원칙 때문에 호출 수가 늘지만, 무리한 매수를 막는 가장
효과적인 장치라 이 비용은 감수한다.

## 3. 측정에 대해

### 왜 백테스트 수익률을 믿으면 안 되나

정량 모델의 룩어헤드 편향은 코드로 막을 수 있다. 하지만 LLM은 2024년 뉴스를 읽으면
그 뒤에 주가가 어떻게 됐는지 이미 학습해서 알고 있고, 이건 모델 가중치 안에 있어서
막을 방법이 없다.

**LLM 컴포넌트가 들어간 시스템의 과거 구간 백테스트 수치는 참고용으로도 위험하다.**
워크포워드 또는 실시간 모의투자로만 검증한다.

### 왜 IC인가

IC(information coefficient)는 예측값과 실제 수익률의 순위상관이다.
0.03~0.05만 안정적으로 나와도 쓸 만한 신호다.

수익률부터 보면 몇 개 종목이 우연히 터진 것을 실력으로 착각하게 된다. IC를 먼저 보면
"신호가 전반적으로 방향을 맞히고 있는가"를 종목 수 전체에 걸쳐 확인할 수 있다.

## 4. 빅데이터 예측 모델에 대한 판단

### 왜 지금 넣지 않나

"데이터를 더 많이 넣으면 예측이 좋아진다"는 가정은 주식에서 잘 성립하지 않는다.
금융 시계열은 신호 대 잡음비가 극단적으로 낮아서, 데이터를 10배로 늘려도 모델이
학습하는 건 대부분 잡음이다. 시장 구조가 바뀌기 때문에 오래된 데이터는 오히려 해롭다.

규모 감각도 필요하다. KOSPI200 × 10년 일봉은 약 50만 행으로, 노트북 pandas에서 도는
크기지 빅데이터가 아니다. 진짜 빅데이터가 되려면 틱·호가창 레벨로 내려가야 하는데,
그 순간 인프라 비용이 급증하고 얻는 알파는 개인이 접근하기 어려운 초단타 영역이다.

그리고 더 근본적으로 — 이전 실패의 원인이 "예측력 부족"이 아니라 "문턱 부재"였다면,
아무리 좋은 모델을 넣어도 성능이 측정되지 않는다. 순서를 지켜야 한다.

### 넣게 된다면

가격 방향 이진 분류는 승률 52~53%가 현실적 천장이고 거래비용 빼면 남는 게 없다.
대신 이런 타깃이 낫다:

| 타깃 | 근거 |
|---|---|
| 횡단면 랭킹 (오늘 200종목 중 상대 순위) | 시장 방향을 맞힐 필요가 없어짐. 노이즈가 적음 |
| 변동성 예측 | 실제로 예측 가능성이 높은 몇 안 되는 영역. 포지션 사이징에 직접 쓰임 |
| 이벤트 후 이상수익률 | 공시 분석가와 직결. 라벨링이 명확하고 이벤트 스터디로 검증 가능 |

구조상으로는 별도 에이전트가 아니라 `agent="quant"` 분석가로 붙인다.
이때 `confidence`는 모델의 예측 확률이 아니라 **최근 60일 롤링 IC**로 잡는다.
모델은 틀리고 있을 때도 높은 확률을 뱉기 때문에, 최근 예측력이 무너지면 자동으로
발언권이 줄어들게 만들어야 한다.

## 5. 다음에 결정할 것

- 매도 로직. 현재 설계는 매수 판단만 다루고 있다.
- 공시 분석가의 그래프 구조 — 지분 관계를 backbone으로, 공급망을 보조 엣지로 하는
  설계가 별도로 진행 중. 어댑터로 붙인다.

### 리스크 게이트 수치 (2026-08-08 확정)

| 룰 | 값 | rejected_by |
|---|---|---|
| 종목당 최대 비중 | 15% | `position_limit` |
| 총 노출 한도 | 100% | `total_exposure` |

마일스톤 1의 게이트 구현은 이 수치를 하드코딩된 상수가 아니라 설정값으로 분리해
나중에 백테스트/튜닝 시 코드 수정 없이 바꿀 수 있게 한다.

**일일 손실 한도(-5%)는 2026-08-20에 폐기했다.** 표에서 뺐다. 이유는
`pipeline.check_gate` docstring에 있다 — 요약하면 매수 판단이 개장 전(08:30) 한
번만 도는 구조라 "오늘 손익"이 그 시점에 항상 0이고, 그래서 계산을 채워 넣어도
발동할 수 없는 룰이었다. 장중 서킷브레이커가 필요해지면 게이트가 아니라 집행
단계(execute_open)에 별도로 설계한다.

**섹터 집중도 한도(40%)는 2026-09-01에 폐기했다(사용자 확정).** 표에서 뺐다.
앞의 일일 손실 한도와 성격이 다르다 — 그건 구조상 발동할 수 없는 룰이었지만, 이건
정상 작동하는 룰을 **의도적으로** 뺀 것이다. 근거: 특정 섹터가 한동안 계속 오르는
국면이 실제로 있고, 40% 상한은 그 국면에서 수익을 제한한다. 받아들이는 위험이
커지는 방향이라는 걸 알고 내린 결정이다. 되돌리려면 `pipeline.check_gate`와
`schemas.RiskGateConfig` 두 곳만 보면 된다.

남은 게이트 룰은 `position_limit`과 `total_exposure` 둘뿐이라, 이 둘이 실제로
발동 가능한 상태인지가 그만큼 중요해졌다. `total_exposure`가 하루 여러 건이 승인될 때
누적을 못 보던 문제는 같은 날 고쳤다(docs/CHANGELOG.md 2026-09-01 3차) — 판단 경로가
승인분을 메모리 안에서 포트폴리오에 얹어 다음 후보 판정에 넘긴다.

### 차트 분석가 입력 형태·시세 데이터 소스 (2026-08-08 확정)

- **입력 형태**: 이미지+vision이 아니라 텍스트(OHLCV + 파생 지표 수치)로 먼저
  시도한다. 차트 이미지를 보고 판단하는 것과 동등한 효과를 노리고 지표를
  추세(SMA)·모멘텀(RSI)·거래량·지지저항(최근 고가/저가)까지 커버하도록 구성.
  텍스트로 부족하다고 판단되면 그때 이미지+vision으로 전환한다 — 지금 미리
  만들지 않는다.
- **시세 데이터**: pykrx(무료, 인증 불필요) 대신 **네이버 금융 비공식 차트 API
  스크래핑**을 쓴다. pykrx의 실시간성이 부족하다고 판단해서 사용자가 직접 선택.
  비공식 엔드포인트라 구조가 바뀔 수 있음 — `collectors.py`의 수집 실패는 데이터
  수집 실패 경로로만 재시도한다 (규칙 4).

### 뉴스 분석가 데이터 소스 (2026-08-08 확정)

- **종목 뉴스**: `finance.naver.com/item/news_news.naver?code=<종목코드>` — 네이버가
  이미 종목코드로 정확히 매핑해주는 페이지라 우리 쪽에서 회사명 키워드 매칭을 할
  필요가 없다. **`Referer: finance.naver.com/item/news.naver?code=...` 헤더가
  없으면 빈 결과만 온다** — 이 헤더는 필수다.
- **업종(도메인) 뉴스**: 네이버에 종목처럼 깔끔한 업종별 뉴스 탭이 없다 (업종 상세
  페이지에도 없음, 자체 뉴스검색 기능은 테스트해보니 사실상 죽어 있음 — 항상 0건).
  대신 `finance.naver.com/news/` 전체 시황 허브를 긁어 헤드라인 중 업종명이 포함된
  것만 골라낸다. 회사명 매칭보다 오탐 허용 범위가 넓은 업종 단위라 키워드 매칭이
  실용적으로 괜찮다고 판단. 개별 기사 타임스탬프는 이 페이지에 없다.
- **뉴스 분석가 프롬프트 설계**: 종목 뉴스가 메인 판단 대상, 업종 뉴스는 "이 종목이
  속한 시장 배경" 참고용으로 명확히 구분해서 준다 — 종목 간 비교가 아니라 이 종목
  하나를 둘러싼 맥락이라 규칙 5(종목 비교 금지) 위반이 아니다.
- **개발 중 API 사용 원칙 (사용자 피드백, 2026-08-08)**: 개발·테스트 단계에서는
  Claude API를 실제로 호출하지 않는다 — 모든 자동 테스트는 모킹으로만 돈다. 실제
  API 확인은 `tests/test_live_smoke.py`에 최소 규모(종목 1개)로만 두고, 기본적으로
  스킵된다. 종목 여러 개 × 여러 날 규모의 실측정(`tests/test_live_signal_rate.py`
  같은)은 사용자가 명시적으로 요청하고 비용 규모를 먼저 확인했을 때만 실행한다.

### 공시 분석가 데이터 소스 (2026-08-08 확정)

- **DART(전자공시시스템) Open API**를 그대로 쓴다 — 차트·뉴스처럼 네이버를
  리버스엔지니어링할 필요 없이 금융감독원 공식 API가 있다. `DART_API_KEY`
  환경변수 필요(무료 발급, opendart.fss.or.kr).
- 두 엔드포인트 조합: (1) `corpCode.xml` — 전체 법인의 종목코드↔고유번호(corp_code)
  매핑을 ZIP으로 한 번에 받아 프로세스 생애주기 동안 메모리 캐시(자주 안 바뀌는
  데이터라 파일 캐시까지는 불필요), (2) `list.json` — corp_code로 종목별 공시 목록
  조회. **corp_code 없이 조회하면 전체 법인 대상 검색이 되어 종목당 독립 호출
  원칙(규칙 5)이 깨지므로 항상 corp_code를 채워서 요청한다.**
- `status="013"`(조회된 데이터 없음)은 에러가 아니라 정상적인 0건 상태로 처리 —
  뉴스 수집기의 "0건 vs 수집 실패" 구분과 동일한 패턴.
- **공시 원문(본문)은 가져오지 않는다** — 보고서명(`report_nm`) 자체가 한국 공시
  특성상 정보 밀도가 높아 뉴스 분석가와 같은 스코프(헤드라인/제목만)로 맞췄다.
  원문 크롤링은 나중에 필요성이 확인되면 추가.

### 마일스톤 3 착수 — IC 측정은 인프라만, 오늘 숫자는 안 나온다 (2026-08-08)

차트·뉴스·공시 세 분석가가 다 붙어서 §3(측정) 단계로 넘어갔다. 여기서 중요한 제약을
다시 확인함: **오늘 당장 IC를 계산할 수 없다.** IC는 (그날 예측 점수, 그 이후 실현
수익률)의 순위상관인데, 뉴스·공시 수집기는 "오늘 시점" 데이터만 긁어오지 과거 특정
날짜의 스냅샷을 재구성하지 못한다 — 그리고 설사 됐다 해도 §3이 이미 명시한 대로
LLM 컴포넌트에는 백테스트 대신 워크포워드·실시간 모의투자만 쓰라고 못 박혀 있다.

그래서 이번에 만든 건 **인프라**뿐이다 (`src/evaluation.py`):
- `information_coefficient(pairs)` — 스피어만 순위상관, 순수 파이썬(외부 의존성 없음).
- `compute_forward_return(ticker, as_of, forward_days)` — 차트 수집기(무료)로 실현
  수익률 계산. `as_of` 이후 데이터가 아직 없으면 None — 이게 "시간이 지나야 한다"는
  제약이 코드로 드러나는 지점이다.
- `summarize_ic(log_path, forward_days)` — 로그에 쌓인 예측과 실현 수익률로 일별
  횡단면 IC의 평균·표준편차 계산.

실제로 IC 숫자를 얻으려면: 앞으로 매일 파이프라인을 실제로 돌려 `logs/pipeline.jsonl`
(임시 tmp_path 말고 진짜 경로)에 예측을 쌓고, 며칠~몇 주 뒤 `summarize_ic`를 돌린다.
`run_day`가 남기는 로그에는 이제 `avg_score`/`avg_confidence`가 필드로 들어간다
(전에는 `Decision.reason` 문자열 안에만 있었음).

### 판단 계층 구현 — 강세/약세 토론 + 포트폴리오 매니저 (2026-08-08 확정)

`pipeline.propose_decision()`(평균 점수 ≥0.85 문턱)이 임시로 대신하던 "판단: LLM"
계층을 실제로 구현했다 (`src/judgment.py`). 구조: 종목 하나의 분석가 의견을 받아
강세 논거·약세 논거를 **서로의 출력을 못 보게 독립적으로** 생성(`asyncio.gather`)한
뒤, 포트폴리오 매니저가 분석가 의견+양쪽 논거를 종합해 BUY/HOLD를 최종 판단한다.

- **왜 두 방향을 강제로 생성하는가** (docs/PLAN.md §2): LLM은 주어진 근거에 동조하는
  편향이 있다. 강세/약세를 데이터가 한쪽으로 쏠려 있어도 억지로 둘 다 만들게 해서
  균형을 잡는다.
- **규칙 6과의 관계**: 매니저가 BUY를 직접 말해도 규칙 위반이 아니다 — 그건 추천일
  뿐, 그 뒤 리스크 게이트(코드)가 최종 승인권을 갖는다. 매니저의 HOLD는 그대로
  확정(매수 없음)되고 매니저의 BUY는 게이트가 거부할 수 있다는 게 "LLM은 거부권만
  가진다"의 실질적 구현이다.
- **`AnalystOpinion`은 안 건드렸다.** CLAUDE.md가 준 고정 계약(score/confidence/
  evidence만, reasoning 텍스트 없음)이라 토론 단계는 각 분석가의 숫자 패턴만 보고
  논거를 만든다 — 원문 reasoning까지 주려면 계약을 바꿔야 해서 안 했다. 대신 새로
  만든 `DebateArgument`(자유 설계 가능한 신규 타입)와 `Decision.debate`/
  `Decision.evidence`(감사 추적용, 기본값 있는 optional 필드)는 추가했다.
- `pipeline.run_day()`가 `judge_fn` 파라미터를 요구하도록 바뀌었다 — 기본값 없음,
  호출부가 항상 명시적으로 골라야 한다. 비용 없는 더미/측정용은
  `pipeline.propose_decision`(그대로 유지, 삭제 안 함), 실제 판단은
  `judgment.judge`.

### 정량 사전 필터 (2026-08-08)

코스피200 전체에 분석가를 돌리면 하루 800회 호출이라(§2) `pipeline.quant_prefilter`를
LLM 분석가 앞단에 뒀다. **품질 필터가 아니라 비용 게이트**다 — "이 종목이 좋다"가
아니라 "오늘 이 종목에 평소보다 뭔가 있다"만 판정하고, 방향 판단은 전적으로 LLM
분석가 몫으로 남긴다.

세 조건을 OR로 절대 문턱 판정(`pipeline.passes_quant_filter`):
- 거래량이 20일 평균 대비 2배 이상
- RSI14가 70 이상(과매수) 또는 30 이하(과매도)
- 코스피200 지수 대비 5일 초과수익률 절대값 5% 이상

top-N이 아니라 절대 문턱이라 통과 개수는 매일 다르고 0일 수도 있다(규칙 2·3).
세 값 다 관행값(RSI 30/70은 Wilder 원안, 나머지는 흔한 스크리너 휴리스틱)으로
시작했고, 이 프로젝트 데이터로 튜닝한 값이 아니다 — 나중에 필터 통과율 로그가
쌓이면 그 분포(과하게 관대한지/인색한지)를 보고 조정하되, 과거 수익률에 맞춰
역산하지 않는다(그건 §3이 경고하는 backtest 함정과 같은 종류의 문제).

**레짐 강건성**: 수익률 조건을 종목 절대 수익률이 아니라 지수 대비 초과수익률로
잡았다 — 시장 전체가 같이 움직이는 날(폭락/급등)에 대부분 종목이 동시에 걸려서
정확히 비용이 가장 크게 튀는 날 후보가 쏠리는 걸 막기 위해서다. 거래량·RSI
조건은 여전히 개별 종목 절대값이라 이 한계가 남아있다 — 의도적으로 남겨둔
디자인이다: "레짐 분류기"를 따로 만들어 문턱을 자동 조정하는 방식은 나중에
"레짐이 안 좋으니 문턱을 조정하자"는 식으로 규칙 2·3을 우회하는 통로가 될 위험이
있어서, 대신 실제로 후보가 몰리면 로그에 그대로 남기고 사용자가 보고 판단하게
둔다 — 자동으로 걸러내지 않고 투명하게 노출.

### 정량 필터 실측 결과 및 수정 — 초과수익률 정규화 (2026-08-08)

구현 직후 코스피200 199종목 전체로 실측했더니 **188/199(94.5%)가 통과했다** —
비용 게이트로서 사실상 기능을 못 하는 수준. 원인을 종목별로 분해해보니
`excess_return` 조건 하나가 거의 전부를 만들고 있었다(150종목은 이 조건
하나로만 통과, 거래량·RSI는 추가로 걸러낸 게 0건). 그날 코스피200 지수가
5일간 -6.9% 빠졌던 게 원인 — **지수가 크게 움직인 주엔 종목 간 수익률 분산
자체가 커져서, 지수 대비 고정 5%p 문턱으로는 대부분의 종목이 걸린다.** 절대
수익률 문턱이 가진 레짐 취약성을 지수 대비로 옮겼을 뿐 근본 문제(고정폭이
변동성 변화에 안 맞음)는 그대로 남아있었던 것.

이 하루치 숫자에 맞춰 문턱값을 손으로 조정하는 건 하지 않았다 — 오늘 딱 맞는
값을 찾아도 다음에 조용한 주가 오면 또 안 맞고, 이건 top-N을 다른 자리에서
재현하는 것과 같은 함정이다. 대신 구조를 고쳤다: `collectors.compute_indicators`에
`daily_return_stdev_20d`(종목 자신의 최근 20일 일별 수익률 표준편차)를 추가하고,
초과수익률을 고정 %p가 아니라 **이 값을 5일치로 스케일(×√5)한 "기대 변동폭"
대비 몇 배인가(z-score)**로 판정하도록 바꿨다(`QUANT_EXCESS_RETURN_Z_THRESHOLD = 2.0`).

시장이 흔들리는 주엔 종목 자신의 변동성도 같이 커지므로 문턱이 자동으로
따라 올라간다 — 매일 일정 비율이 통과하도록 구조적으로 보장하는 횡단면
z-score(반려한 방식, 규칙 2·3 우회 소지)와 달리 종목 자신의 시계열 대비라
그런 보장이 없다.

수정 후 같은 199종목으로 재검증: 94.5% -> 41.2%로 절반 넘게 줄었다. 다만
41.2%도 여전히 높다 — 자기 변동성 정규화는 후행 지표(최근 20일 평균)라
레짐이 막 바뀌는 시점엔 "정상 변동폭" 기준 자체가 아직 낮아서 일시적으로
과민하게 반응하는 게 정상이다. 이 숫자 하나에 맞춰 문턱을 더 조이지 않았다 —
그러면 오늘 하루에 과적합하는 것과 같은 함정이다. 여러 날(특히 조용한 날
포함) 로그가 쌓인 뒤 분포를 보고 판단한다.

### 매도 로직 1단계 — 결정론적 안전장치 (2026-08-09 확정)

CLAUDE.md가 "아직 정해지지 않은 것"으로 남겨뒀던 매도 로직에 착수했다. 매수와
근본적으로 다른 지점이 있다는 게 설계의 핵심 전제: 매수는 판단을 미루면 현금
(안전)이지만, 매도는 판단을 미루면 손실 종목을 계속 들고 있는 것이라 "판단
안 함 = 안전"이 성립하지 않는다. 그래서 순수 LLM 재량 대신 **결정론적 안전장치
+ LLM 재량 하이브리드**로 가기로 했고, 이번엔 안전장치만 구현했다(`src/sell.py`,
`pipeline.py`와 분리 — 고치는 이유가 다름).

**확정 수치**:
- 손절선: 진입가 대비 -10% (`STOP_LOSS_PCT`) — 전량 매도.
- 익절: 진입가 대비 +20%에서 첫 트리거, 전량이 아니라 **현재 보유량의 1/3만
  매도**하고 계속 들고 간다 — 상승 여지를 남겨두기 위해서다.
- 이후엔 진입가가 아니라 **고점 대비 트레일링 스톱**으로 전환: 고점에서 일정
  비율(`TAKE_PROFIT_TRAIL_PCT`, 제안값 -7% — 사용자가 정확한 수치를 아직
  확정 안 함, 관행값으로 시작 후 로그 보고 조정) 조정되면 다시 1/3 매도.
  트리거가 발동할 때마다 고점을 그 시점 가격으로 리셋한다 — 안 그러면 같은
  하락 하나로 여러 단계가 연달아 발동해버린다.
- 이 사이클은 상한 없이 반복된다 — 강제로 3번에서 끊지 않는다. `(2/3)^n`이라
  전량 청산되는 일 없이 항상 일부가 남아 계속 상승 여지를 갖는다(사용자
  의도 그대로).

**고점을 무엇으로 재는가 (2026-09-02 확정)**. 트레일링만 기준이 *고점*이고, 그
고점은 하루 사이에도 올라간다. 손절과 첫 익절은 기준이 *진입가*라 고정이다. 이
비대칭에서 두 가지가 따라온다.

1. **당일 저가/고가로는 트레일링을 판정하지 않는다.** 당일 저가가 고점보다 먼저
   찍혔는지를 알 수 없어서, 가격이 *올라가* 고점이 갱신되는 순간 이미 지나간
   저가가 트레일 라인 아래로 들어간다. 2026-09-02 192820이 그렇게 팔렸다(저가
   09:00, 고가 13:28). 손절은 순서와 무관하므로 구간 판정에 그대로 남는다 —
   놓치면 손실이지만, 트레일링을 놓치는 건 이익 축소라 감수 가능하다.
2. **매도 후 고점 리셋은 그날 하루 유효로 기록한다**(`Position.peak_reset_day`).
   당일 고가는 리셋 이전 구간을 포함하고 `day_high >= 현재가`는 항상 참이라,
   기록해두지 않으면 리셋이 다음 회차에 반드시 되돌아온다. 그러면 트리거가 된
   고점이 그날의 고가일 때 매분 재발동해 -7% 반락 한 번에 전량이 나간다 —
   "항상 일부가 남는다"는 위 의도와 정면으로 어긋난다.

**규칙 6과의 관계**: 리스크 게이트는 "새 매수를 막는" 장치다. 결정론적 매도는
게이트를 거치지 않는다 — 보유분을 줄이는 행위 자체가 위험을 낮추는 방향이라
"한도 초과" 개념이 성립하지 않는다.

**스키마**: `Position`에 `entry_price`/`peak_price`/`take_profit_stage` 추가.
`entry_price`가 `None`인 포지션은 매도 평가 자체를 건너뛴다 — `AnalystOpinion`이
"판단 불가"와 "판단했으나 기각"을 구분하는 것과 같은 패턴. 매도는 `Decision`과
완전히 분리된 `SellAction` 타입으로 만든다 — `Decision.action` 주석이 애초에
"매도는 별도 경로"라고 못 박아뒀다.

**알려진 갭 — 매수 실행 경로가 아직 진입가를 안 채운다**: `pipeline.execute()`
(신규 매수 실행)는 지금 가격 정보를 전혀 다루지 않아서(`weight`만 씀),
`Position.entry_price`가 실제로 채워지지 않는다. 매도 로직이 실제로 작동하려면
매수 시점에 현재가를 어디서 가져와 `entry_price`/`peak_price`를 초기화할지
먼저 결정해야 한다(예: 판단에 쓰인 `MarketContext`의 최신 종가를 `Decision`까지
끌고 올지, 아니면 집행 시점에 KIS로 별도 시세를 다시 조회할지). 다음 단계로
남겨뒀다.

**아직 구현 안 함**: LLM 재량 매도(분석가가 보유 종목을 재평가해 "확신이
무너졌다"고 판단하면 매도를 제안하는 경로) — 결정론적 안전장치가 먼저 자리잡은
뒤에 얹기로 했다.

### 진입가 배선 — 실제 KIS 모의투자 주문 집행 (2026-08-09 확정)

위에서 남겨뒀던 갭(매수 실행 경로가 진입가를 안 채움)을 실제로 풀었다. 판단은
전일 데이터로 미리 해두더라도, 집행은 시장가 주문 + 갭 체크로 하기로 했다 —
사용자 확정: "전날 종가 기준으로 다음날 매수를 걸어놓으면 안 사질 때도 있다"는
게 이유. 장 시작가가 전일 종가 대비 ±3%(사용자 확정치) 넘게 벌어지면 판단
근거가 낡았다고 보고 매수를 스킵한다 — 강행하지 않는다는 점에서 규칙 2·3과
같은 정신.

**`src/kis.py`에 추가된 것**: `fetch_current_price`(실시간 현재가),
`fetch_account_balance`(계좌 총평가금액 — `PortfolioState`는 비중만 들고 절대
금액을 안 쌓아서, 비중을 실제 주수로 환산하려면 매번 브로커를 잔고의 출처로
삼는다), `place_market_buy_order`(시장가 매수 주문 접수, 주문번호 반환),
`fetch_fill_price`(그날 그 종목의 평균 체결가 — 주문별 체결 내역이 아니라
집계 필드 `pchs_avg_pric`를 쓴다). GET 전용이던 `_kis_get`을 `_kis_request`로
리팩터링해 POST(`_kis_post`, 주문 접수용)까지 공통 재시도·쓰로틀링 로직을
공유하게 했다.

**라이브로 실측 검증한 것(2026-08-09)**: 계좌번호 상품코드가 "01"임을 확인
(잔고조회 정상 응답), 잔고조회 API가 사용자가 설정한 초기자금 1억원과 정확히
일치하는 `tot_evlu_amt`를 반환함을 확인, 현재가 조회 정상 확인. **주문 접수는
구조만 확인됐다** — 파라미터·계좌 인증은 정상 처리됐지만 응답이 "모의투자
영업일이 아닙니다"(그 시점 장이 닫혀 있었음)라 실제 체결까지는 못 봤다.
체결가 조회의 `output1`(주문별 상세) 필드명은 실제 체결 건이 없어 확인 못
했고, 대신 필드명이 이미 확인된 `output2`(집계) 쪽으로 우회했다. **장중에
실제 매수가 한 번 나가면 이 부분을 재검증해야 한다.**

**`pipeline.execute_buy_order`(신규, 비동기)**: 기존 `execute()`(순수 함수,
가격 개념 없는 시뮬레이션 전용, 무비용 테스트 경로로 계속 남김)와 분리했다.
갭 체크 → 잔고 조회 → 수량 계산(`floor(총평가금액 x weight / 현재가)`) → 주문
접수 → 체결가 조회 → `Position.entry_price`/`peak_price` 설정 순서. 가격·잔고
조회 실패나 주문 거부 등 어느 단계에서든 실패하면 매수 없이 그대로 반환한다
(규칙 1: 기본 상태는 현금). 기존 포지션에 추가매수하는 경우는 비중 가중평균으로
진입가를 갱신하는데, `weight`가 "그 시점 총자산 대비 비중"이라 총자산이 매수마다
달라지면 완전히 정확하진 않은 근사치다 — 추가매수는 드문 경로라 이 정도면
충분하다고 판단.

### 매도 로직 일별 배선 — evaluate_holdings (2026-08-09)

`src/sell.py`의 손절/트레일링 익절 평가 함수들이 그동안 파이프라인 어디에서도
호출되지 않고 있었다 — `pipeline.evaluate_holdings()`로 매일 실행되게 연결했다.

매수 쪽엔 정량 필터가 있지만 이쪽엔 없다. 필요가 없기 때문이다: 리스크
게이트가 종목당 최대 비중을 15%로 막아둬서 보유 종목 수 자체가 원천적으로
적다(최대 ~7개). 그래서 비용 게이트 없이 보유 종목 전부를 매일 그냥 평가한다.

흐름: 보유 종목 전체의 현재가를 KIS로 동시 조회(`asyncio.gather`) → 고점
갱신(`sell.update_peak_price`) → 손절/익절 평가(`sell.evaluate_deterministic_sell`)
→ 트리거되면 집행(`sell.execute_sell`) → `logs/sell.jsonl`에 기록. 가격 조회가
실패한 종목은 그날 평가를 건너뛴다 — collectors/kis 단에서 이미 재시도를
소진한 뒤라 여기서 다시 재시도하지 않는다(규칙 4). 한 종목의 실패가 다른
보유 종목 평가를 막지 않는다.

LLM 재량 매도는 여전히 미구현 — 결정론적 안전장치만 이 함수로 매일 돈다.

### LLM 재량 매도 + 실주문 배선 완성 (2026-08-09)

남아있던 두 갭(LLM 재량 매도 미구현, 실제 주문 집행이 판단 체인에 안 이어짐)을
마저 이어붙였다.

**LLM 재량 매도**: 매수 쪽 강세/약세 토론 + 포트폴리오 매니저와 대칭 구조로
만들었다(`judgment.debate_holding`, `judgment.portfolio_manager_sell`,
`judgment.judge_sell`). 매수용 프롬프트를 재사용하지 않고
`prompts/debate_stay.md`/`debate_exit.md`/`portfolio_manager_sell.md`를 새로
썼다 — "매수할까"와 "계속 들고 있을까"는 다른 질문이라 매수용 프레이밍을
그대로 쓰면 LLM이 엉뚱한 질문에 답하게 된다. `DebateArgument.stance`는
bull=존버/bear=이탈로 그대로 재사용(신규 stance 불필요).

규칙 6과 다르게 설계한 지점: 매수용 포트폴리오 매니저는 게이트가 뒤에서
거부할 수 있다는 전제로 "적당히 관대해도 된다"고 프롬프트에 명시하는데,
매도용 매니저는 정반대로 "네 SELL은 그대로 실행된다, 그러니 확신 없으면
HOLD가 기본"이라고 프롬프트에 명시했다 — 게이트가 없는 대신 프롬프트 자체의
보수성으로 상쇄한다.

`pipeline.evaluate_holdings`에 `analyst_fn`/`judge_sell_fn`을 옵션으로
추가했다(기본값 `None` — 안 넣으면 이 계층 자체가 꺼진다). 결정론적 매도가
이미 트리거된 종목은 LLM에게 다시 묻지 않는다(코드가 이미 팔기로 정한 걸
재확인할 이유가 없다). analyst_fn/judge_sell_fn을 옵션(None 기본)으로 둔 건
`execute_fn`류(기본값 없음, 항상 명시)와 의도적으로 다른 결정이다 —
결정론적 안전장치는 항상 켜져 있어야 하지만, LLM 재량은 진짜 선택적 추가
비용이라 안 켜는 쪽이 안전한 기본값이다.

**실주문 배선**: `run_day`/`run_daily`가 `execute_fn`을 필수 인자로 받도록
바꿔서 `execute_buy_order`(실제 KIS 주문)를 실제로 꽂을 수 있게 했다 —
이전엔 이 함수가 있어도 아무도 안 불렀다. 무비용 시뮬레이션 경로는
`execute_simulated`(`execute()`의 비동기 래퍼)로 남겨 기존 테스트가 그대로
돌게 했다. 매도도 대칭으로 `SellExecuteFn`(`execute_sell_simulated` vs
`execute_sell_order`)을 만들어 `evaluate_holdings`에 필수 인자로 추가했다.

**실제 매도 주문을 위해 필요했던 것**: `Position`에 `quantity`(실제 보유
주수)를 추가했다. `weight`는 비중일 뿐이라 매도 시 몇 주를 팔지 알 수
없었다 — `execute_buy_order`가 실제로 주문을 넣은 수량을 그대로 저장해두는
쪽을 택했다(브로커를 다시 조회하는 대신 — 이미 우리가 아는 값이라 조회할
필요가 없고, 미검증 필드명에 의존하는 리스크도 없다). `quantity`가 없는
포지션(순수 시뮬레이션 `execute()`로 연 포지션)은 실제로 판 적이 없으니
`execute_sell_order`가 실주문 없이 상태만 시뮬레이션으로 갱신한다.

`kis.py`에 `place_market_sell_order` 추가 — `place_market_buy_order`와 완전히
대칭(같은 엔드포인트, tr_id만 다름). 매수와 마찬가지로 라이브로 구조 검증만
했다("모의투자 영업일이 아닙니다" 응답 — 계좌·파라미터는 정상 처리 확인,
실제 체결은 장중 재검증 필요).

### 정량 필터 상한 재검토 — 상한 없음으로 확정 (2026-08-09)

AWS에 올려 스케줄러로 매일 자동 실행하기로 하면서, 사용자가 "정량 필터 통과
종목을 15개로 상한을 걸어야 하는 것 아니냐"고 확인을 요청했다. 확인 결과:
**`quant_prefilter`엔 상한이 코드로도, 설계상으로도 없다.** 세션 초반에 내가
"~15개 정도 나올 것 같다"고 말한 적은 있지만 그건 예상치였을 뿐, 실제 구현
시점엔 규칙 2(목표 신호 개수 금지, top-N 선택 금지)에 따라 절대 문턱만 쓰고
개수 상한을 의도적으로 넣지 않았다 — 상한을 걸려면 통과 종목 중 "상위 N개"를
추릴 기준이 필요한데, 그건 이전 프로젝트를 무너뜨린 패턴(문턱을 우회해 억지로
채우기)과 방향만 반대일 뿐 같은 종류의 문제(정해진 개수를 맞추려고 뭔가를
선택)다.

토큰 비용 우려가 실제로 근거가 있는지 계산해봤다: 종목 1개가 필터를 통과해
끝까지 가면 LLM 호출 6회(분석가 3 + 토론 2 + 매니저 1), 종목당 약 $0.015
(Sonnet 5 인트로가 기준). **200종목이 전부 통과하는 최악의 경우에도 하루
$3~4.5 수준**(정가 기준으로도 $4.5) — 우려했던 것만큼 크지 않다는 게 확인됐다.
이 숫자를 보고 사용자가 상한 없이 그대로 가서 실측 데이터로 나중에 보정하는

AWS 배포 직후 남겨뒀던 두 갭(휴장일에도 cron이 그대로 돌아 비용 낭비, cron 실패가

이미 채워져 있는지 타이밍이 불확실해서 판정 자체가 불안정해진다. 대신 KRX가 연초에
미리 공표하는 2026년 휴장일 15개를 정적으로 박아뒀다(`is_krx_trading_day`, 요일

갱신 전) 조용히 잘못된 판단을 내리는 대신 `ValueError`를 던지도록 했다 — 이건 규칙
4가 금지하는 "결과가 마음에 안 들어서 재시도"와는 다른 종류의 유지보수(알려진
스케줄을 옮겨적는 작업)라 매년 갱신이 필요해도 우회로 보지 않는다.
`scripts/run_daily.py`의 `main()` 맨 앞에서 KST 기준 오늘 날짜로 체크해서, 거래일이
아니면 어떤 LLM/KIS 호출도 없이 즉시 반환한다.

**cron 실패 알림 (`src/notify.py`)**: 텔레그램 봇으로 발송(사용자가 이메일/Slack/
Discord/SNS 중 텔레그램을 선택). 알림 전송 자체가 실패해도 예외를 삼킨다 — 알림
실패 때문에 원래 실패의 로그(`logs/cron.log`)가 안 남으면 SSH로도 원인 파악할
방법이 사라지기 때문이다. `run_daily.py`에 두 지점에서 건다: (1) `evaluate_holdings`
실패 시(매수 판단은 계속 진행하는 기존 흐름은 유지, 알림만 추가), (2) `main()`
전체가 예외로 죽을 때(알림 보낸 뒤 그대로 재raise해서 cron의 실패 종료 코드는
유지). 토큰/chat_id는 사용자가 직접 `.env`에 채워 넣는 방식으로 전달받았다 — 채팅
전달은 시크릿이 대화 기록에 영구히 남는 문제가 있어 배제(과거 AWS 루트 키 노출
사고와 같은 이유). 로컬 `.env`를 EC2 `~/sima/.env`로 그대로 동기화해서 반영.

### 실거래 데이터로 학습하는 quant 분석가 — 방향만 합의, 구현은 보류 (2026-08-09)

자동매매가 돌기 시작하면서 사용자가 "이 프로젝트 자체가 쌓는 실거래 데이터(진입
시점 지표 → 실제 이후 수익률)로 학습해서 판단에 참고하면 어떻겠냐"고 제안했다.
이전 프로젝트를 무너뜨린 버그(재시도가 사실상 매수 할당량으로 작동)와는 인과관계가
반대라는 점은 맞다 — 다만 **어떻게 반영하는지**에 따라 안전/위험이 갈린다는 점을
짚고 넘어갔다.

- **안전한 형태**: 축적된 실거래 결과로 별도의 `quant` 분석가(통계/ML 모델)를
  학습시켜 다른 분석가와 동일하게 종목당 독립 호출로 `AnalystOpinion` 하나만
  내놓게 하는 것. 규칙 5(종목 간 비교 금지)·6(LLM은 거부권만)과 충돌하지 않는다 —
  "정량 ML 분석가" 항목으로 이미 열어둔 결정과 같은 방향(§"아직 정해지지 않은 것").
- **위험한 형태**: "전에 이런 상황에서 사서 이렇게 됐다"는 서술을 LLM 프롬프트에
  직접 끼워 넣는 것. 시간축으로 종목 비교를 우회하는 셈이고, 최근 성과에 판단이
  정서적으로 결합될 위험이 있다(문턱을 낮추는 대신 판단을 위축시키는 방향이라도
  "그날의 증거가 아닌 다른 것에 판단이 좌우된다"는 점에서 같은 종류의 문제).

또한 지금은 실거래 데이터가 0건(첫 주문이 아직 안 나감)이라 학습할 표본 자체가
없다 — 정량 필터 초과수익률 임계값을 튜닝할 때 이미 겪은 "관측치 하나로 과적합"
함정과 같은 리스크다.

**결정**: 방향(안전한 형태 = 별도 `quant` 분석가로만 반영)에는 합의했지만, 구현은
실거래 데이터가 유의미하게 쌓인 뒤로 미룬다. 지금 코드 변경 없음.

### 감시 지표 자동 집계 (2026-08-09)

CLAUDE.md "감시 지표" 섹션이 요구하는 3가지(최근 20영업일 매수신호 비율, 게이트
거부사유별 건수, 분석가별 호출수·실패율·토큰사용량) 중 앞 둘은 `pipeline.summarize_log`
함수로 이미 계산 가능했지만 **아무 데서도 호출되지 않고 있었고**, 뒤 하나는 집계
코드 자체가 없었다(`llm.py`가 호출마다 토큰은 로그로 남기지만 어떤 분석가 호출인지
식별할 라벨이 없어 사후에 분석가별로 못 나눴다).

**`llm.call_structured`에 `label` 파라미터 추가**: 이 함수는 차트/뉴스/공시
분석가와 토론(bull/bear/stay/exit)·매니저(매수/매도)가 전부 공유하는 단일 통로라,
여기서 라벨을 안 남기면 사후에 호출을 분석가별로 귀속시킬 방법이 없다. 매 호출의
최종 결과(성공/실패, 시도 횟수, 누적 input/output 토큰)를 `logs/llm_calls.jsonl`에
한 줄씩 남긴다 — `pipeline.py`의 `_append_log`와 같은 JSONL 적재 패턴을 그대로
따랐다(모듈이 달라 순환 임포트를 피하려 `llm.py`에 작게 중복 구현).

**`pipeline.summarize_recent_trading_days`**: 기존 `summarize_log(total_days)`는
로그 파일 전체를 total_days로 나누는 구조라 "정확히 N일치만 담긴 로그"를
전제한다(마일스톤1 시뮬레이션 테스트가 그렇게 씀) — cron이 매일 같은 파일에 계속
이어 쓰는 실환경에서는 이 가정이 깨진다. 로그에 남은 서로 다른 날짜 중 최근
n_days개만 추려서 그 위에서 집계하는 래퍼를 새로 추가했다(기존 `summarize_log`는
테스트 호환을 위해 그대로 둠).

**`pipeline.summarize_llm_calls`**: `logs/llm_calls.jsonl`을 label별로 묶어
호출수·실패율·토큰합계를 낸다. `since` 파라미터로 최근 창(달력일 30일 ≈ 영업일
20일 — 리포트 조회창일 뿐이라 정밀할 필요 없음)만 볼 수 있다.

**`scripts/run_daily.py`가 매일 실행 끝에 두 집계를 로그로 남긴다**
(`_log_monitoring_summary`, `monitoring_signal_rate`/`monitoring_llm_calls` 로그
라인 — `logs/cron.log`로 그대로 흘러간다). **의도적으로 읽기 전용이다**: 이 집계
결과를 판단 로직 어디에도 입력으로 되먹이지 않는다 — 방금 위 항목에서 짚은 "과거
데이터가 판단에 개입하면 위험하다"는 원칙을 모니터링 자체에도 그대로 적용한 것.

### 매매일지용 체결 기록 — `logs/trade_journal.jsonl` (2026-08-09)

사용자가 "로그를 최대한 많이 남기고 싶다"고 요청하면서, 나중에 노션과 연결해
매매일지(포트폴리오 서사)를 쓸 때 필요한 데이터가 지금 안 남고 있는지 점검했다.
사람이 나중에 수동으로 채울 여지(메모·태그 등)는 없고 **전부 자동 기록만** —
사용자가 명시적으로 확인.

점검 결과 실제로 큰 구멍이 있었다: `pipeline.jsonl`/`sell.jsonl`은 "판단이
게이트를 통과했는지"까지만 기록하고, **실제 체결 사실(체결가·수량·주문번호)과
그 판단을 만든 근거(분석가 의견·토론 논거·매니저 사유)는 어디에도 구조화된
형태로 안 남고 있었다.** 갭 초과/잔고 조회 실패로 매수가 스킵돼도
`pipeline.jsonl`엔 `approved: true`로만 남아 실제로는 안 산 걸 산 것처럼 보이는
상태였다. 실현손익(realized P&L)을 계산하는 코드도 전혀 없었다.

**대응**: 판단 로그(`pipeline.jsonl`/`sell.jsonl`, "게이트가 뭘 걸렀나" 관점)는
그대로 두고, 별도로 `logs/trade_journal.jsonl`을 추가해서 **실제 체결이 일어나는
지점**(`execute_buy_order`/`evaluate_holdings`)에서 한 이벤트당 한 줄씩 남긴다.

- **매수 이벤트**: 체결가·수량·KIS 주문번호·갭 비율 + `decision.model_dump()`
  전체(분석가별 점수·evidence, 강세/약세 토론 논거, 매니저 최종 사유) — 개별
  필드를 손으로 골라서 남기지 않고 `Decision` 객체를 통째로 직렬화했다. 나중에
  `Decision`에 필드가 늘어도 로그가 자동으로 따라가고, 지금 당장 어떤 필드가
  "매매일지에 중요한지" 미리 고르지 않아도 된다.
- **매도 이벤트**: 매도 사유(`stop_loss`/`take_profit_trail`/`llm_discretionary`),
  LLM 재량 매도일 때의 실제 판단 사유 텍스트(`SellAction.reasoning` — 이전엔
  `portfolio_manager_sell`이 생성만 하고 버렸다), 체결가, 진입가 대비
  실현손익률, 보유일수.

**스키마 변경 (최소, 기존 계약 안 건드림)**: `Position.entry_day: date | None`
(최초 진입일 — 추가매수해도 갱신 안 함, 보유기간 계산용), `SellAction.reasoning:
str | None`(결정론적 매도는 룰이 근거 그 자체라 None으로 남는다). 둘 다 optional
필드 추가라 `Decision.debate`/`Decision.evidence`를 추가했을 때와 같은 패턴.

**보유기간·실현손익 계산 위치**: `evaluate_holdings`가 실제 매도를 실행하기
직전의 `position`(entry_price/entry_day 보존된 상태)과 `current_price`를 그대로
갖고 있어 여기서 계산한다 — `sell.execute_sell_order`는 체결가를 별도로 다시
조회하지 않고(매수 쪽 `fetch_fill_price`와 비대칭 — 아직 안 맞춤, 장중 재검증
과제 중 하나) `current_price`를 그대로 체결가로 쓰기 때문에 이 지점의 값이
정확하다.

### 노션 연동 — 포트폴리오 워크스페이스 (2026-08-09)

`src/notion_sync.py`. 노션 REST API를 `requests`로 직접 호출한다(SDK 미사용 —
`kis.py`/`collectors.py`와 같은 패턴, 재시도는 네트워크 오류와 429만, 그 외
4xx는 재시도해도 같은 응답이라 즉시 실패 처리). 사람이 나중에 수동으로 채울
필드는 없다(사용자 확정) — `logs/trade_journal.jsonl`이 유일한 원천이고 이
모듈은 그걸 노션이 읽기 좋은 형태로 옮기기만 한다.

**워크스페이스 구조**(사용자가 미리 만들어 integration과 연결해둔 페이지를
랜딩 페이지로 그대로 쓴다 — 새 페이지를 만들지 않는다): 랜딩 페이지에 소개+
GitHub 링크 블록만 붙이고(`add_landing_page_content`), 하위에 "프로젝트 소개·
설계 철학" 페이지(`create_intro_page`)와 "매매일지" 데이터베이스
(`create_trade_journal_database`)를 만든다. 성과 지표(신호율/거부사유/IC)는
따로 안 뺐다 — 사용자가 "그건 일지에 들어갈 만한 것"이라고 판단, IC 정도만
나중에 추가 검토하기로 함.

**소개 페이지는 링크로 넘기지 않고 내용을 페이지 안에 다 적는다**(사용자
요청, 2026-08-09 — 처음엔 "전체 내용은 GitHub 참고"로 짧게 만들었다가 재작성).
아키텍처 다이어그램과 핵심 계약(`AnalystOpinion`/`Decision`/`GateResult`)은
코드 블록으로 원문 그대로 박아넣는다. `_intro_page_blocks()`가 내용의 유일한
소스이고, `create_intro_page`(최초 생성)와 `refresh_intro_page`(기존 페이지의
블록을 전부 지우고 같은 내용으로 재작성 — CLAUDE.md/PLAN.md가 바뀌면 다시
실행)가 이걸 공유한다.

**매매일지 동기화**(`sync_trade_journal`): 보유 종목 스냅샷이 아니라 **전체
이력**이다 — 매수든 매도든 발생한 모든 이벤트가 각각 한 행으로 계속 쌓이고,
청산된 포지션도 행이 지워지지 않는다(포지션을 완전히 팔아도 그 매수/매도
기록은 그대로 남는다 — 매매일지의 목적 자체가 "무슨 일이 있었는지"의 이력이지
"지금 뭘 들고 있는지"의 스냅샷이 아니다). 중복 방지는 노션에 매번 쿼리하는
대신 로컬 파일(`logs/notion_sync_state.json`)에 이미 올라간 이벤트 키
(`event:ticker:day`)를 남기는 방식 — `portfolio_state.json`과 같은 "로컬
파일을 신뢰한다" 패턴. 실패한 이벤트는 키를 안 남겨서 다음 `run_daily.py`

### 일일 리포트 데이터베이스 — 그날 하루 단위 요약 (2026-08-09)

사용자 질문("매매일지엔 현재 보유 종목만 남아, 아니면 전체 과정이 남아?")에
답하면서, 매매일지(`sync_trade_journal`)는 **이벤트 이력**(매수/매도 한 건당
한 행, 청산돼도 안 지워짐)이지 스냅샷이 아니라고 확인해줬다. 그런데 사용자가
원한 건 그것과 다른 것 — "장마감 후 그날 하루: 무슨 판단을 했고, 뭘 샀고,
최종적으로 지금 뭘 들고 있는지"를 한 페이지로 보는 뷰였다. 매매일지를 아무리
필터링해도 이건 안 나온다(그날 왜 다른 종목은 안 샀는지, 즉 게이트 거부·HOLD
같은 "안 산 것"에 대한 정보가 매매일지엔 아예 없다 — 체결된 이벤트만 있으니까).

그래서 별도로 "일일 리포트" 데이터베이스를 추가했다(`create_daily_report_database`,
`sync_daily_report`). 하루 단위로 한 행씩 쌓인다(매매일지처럼 이벤트당 한 행이
아니다). 내용 구성:
- **오늘의 판단 요약**: `logs/pipeline.jsonl`을 그날 날짜로 필터링 — 그날 판단한
  종목 전부(BUY 승인/BUY인데 게이트 거부/HOLD)를 다 보여준다. 매매일지엔 없는
  "안 산 것"의 근거가 여기 있다.
- **매수/매도**: `logs/trade_journal.jsonl`을 그날 날짜로 필터링.
- **장마감 기준 보유 종목**: 그 시점의 `PortfolioState`를 그대로 스냅샷으로 —
  추가 KIS 조회 없이 이미 메모리에 있는 값을 쓴다(리포팅 때문에 실거래 API
  호출을 늘리지 않는다는 기존 모니터링 원칙과 동일).

매매일지와 마찬가지로 중복 방지는 로컬 상태 파일
(`logs/notion_daily_report_state.json`, 날짜 키)로 한다 — 같은 날 cron이
재실행돼도 리포트가 중복 생성되지 않는다. `run_daily.py`가 매일 실행 끝에
매매일지 동기화와 함께 자동으로 호출한다.

`scripts/setup_notion_workspace.py`도 이번에 산출물별 독립 idempotency로
리팩터링했다(전에는 "매매일지 DB 있으면 전체 스킵" 한 덩어리였는데, 이번처럼
나중에 새 산출물이 추가돼도 이미 설정된 나머지를 다시 안 건드리고 빠진
것만 채우게).

### "왜 안 샀는지"·"체결 직전 스킵" 기록 (2026-08-09)

사용자가 매매일지·일일 리포트를 보고 "각 종목을 왜 매수했는지/안 했는지, 그날
매매활동 중 생긴 특별한 일은 어디에 적히는지" 물어서 점검했더니 실제로 두
군데가 비어 있었다.

1. **HOLD·게이트 거부 종목의 실제 판단 문장이 저장 안 되고 있었다.**
   `run_day`가 `pipeline.jsonl`에 남기는 건 `avg_score`/`avg_confidence`
   숫자뿐이고, 매니저가 실제로 생성한 `Decision.reason`(서술)은 로그로
   한 번도 안 남고 버려지고 있었다. `run_day`의 `_append_log` 호출에
   `"reason": decision.reason`을 추가했고, `notion_sync._daily_report_children`이
   이제 각 종목 줄에 이 문장을 같이 보여준다(300자로 자름 — 전체 판단
   구성요소는 애초에 그 결정이 실제 매수로 이어졌을 때만 매매일지에 온전히
   남는다, 그건 원래 설계였다).

2. **게이트는 승인했는데 체결 직전(갭 초과·잔고 조회 실패·수량 0·주문 거부)에
   스킵된 경우가 어디에도 구조화된 형태로 안 남고 있었다.** `pipeline.jsonl`엔
   `approved: true`로만 남아서 마치 산 것처럼 보이는 상태였고(이번 세션 초반에
   한 번 지적했던 문제의 나머지 절반), 실제 상황은 `logger.warning` 자유
   텍스트로 `logs/cron.log`에만 있었다. `execute_buy_order`의 각 스킵 분기에
   `_log_buy_skip()`을 추가해 `trade_journal.jsonl`에 `event: "buy_skipped"`로
   남긴다(초기 게이트 거부 자체는 안 남긴다 — 그건 이미 `rejected_by`로 잡힘,
   여기서 잡는 건 "승인 이후" 단계 실패만). 매매일지 데이터베이스의 "구분"
   select에 "매수스킵" 값이 새로 추가됐다(Notion select 속성은 스키마에 없는
   값을 보내면 API가 자동으로 옵션을 추가한다 — DB를 재생성하거나 스키마를
   미리 고칠 필요 없음). 일일 리포트에도 "특별한 일 — 게이트는 통과했지만
   체결 못 함" 섹션이 새로 생겼다.

이 변경 과정에서 `tests/test_execute_buy_order.py`의 스킵 테스트 4개가
`log_path`를 안 넘기고 있어서(전엔 스킵 시 아무것도 안 남겨서 문제가 없었는데)
실제로 로컬 `logs/trade_journal.jsonl`에 테스트 쓰레기가 쌓이는 걸 발견 —
전부 `tmp_path` 기반으로 고치고 오염된 파일은 삭제했다. **테스트에 새
로그 파라미터를 추가할 때마다 항상 "이 파라미터를 안 넘기는 기존 테스트가
실제 파일에 쓰게 되는 건 아닌지" 확인할 것.**

### 전체 워크플로우 점검 (2026-08-09, 실전 검증 전날)

사용자가 "맨 처음부터 알림/일지 작성까지 전체 워크플로우를 테스트로
점검하자"고 요청. 점검해보니 두 가지가 비어 있었다.

1. **`notify.format_error_alert`를 만들어놓고 실제로는 안 쓰고 있었다.**
   `run_daily.py`의 오류 발신 3곳(evaluate_holdings 실패, 노션 동기화 실패,
   run_daily 전체 실패)이 여전히 직접 f-string을 조립하고 있었다 — "통일된
   양식" 요청의 취지에 안 맞았다. 세 곳 다 `format_error_alert()`를 쓰도록
   고쳤다.

2. **`scripts/run_daily.py`의 오케스트레이션(`main()`) 자체를 검증하는 테스트가
   하나도 없었다.** 개별 단계(`evaluate_holdings`, `run_daily`, `notify`,
   `notion_sync`)는 각자 테스트가 있지만, 그것들이 cron 진입점 안에서 올바른
   순서·인자로 이어지는지는 아무도 확인하지 않고 있었다. `tests/test_run_daily.py`
   를 새로 추가 — 휴장일 스킵, 정상 흐름의 단계 순서(`evaluate_holdings` →
   `run_daily` → 모니터링 → 노션), `evaluate_holdings` 실패 시에도 `run_daily`가
   이전 포트폴리오를 이어받아 계속 진행하는지, `_sync_notion`의 설정/미설정
   분기, 포트폴리오 저장/로드 라운드트립을 검증한다. `main()`이 내부에서
   `_sync_notion`/`_log_monitoring_summary`를 호출하므로, 그 함수들 자체의
   동작을 검증하는 테스트는 모듈 임포트 직후(어떤 몽키패치도 걸리기 전)의
   실제 함수 참조를 미리 붙잡아뒀다가 그걸 직접 호출하는 방식을 썼다 —
   안 그러면 오케스트레이션 테스트용 autouse 픽스처가 덮어쓴 no-op을 대신
   테스트하게 된다.

3. **`tests/test_end_to_end_workflow.py`**: 위 둘로도 "단계별로는 맞는데 실제로
   이어 붙였을 때도 맞는가"는 완전히 검증되지 않는다 — 그래서 `scripts.run_daily.main()`
   을 네트워크 경계(`kis.py`/`collectors.py`의 개별 fetch 함수, `llm.call_structured`,
   `notify.send_telegram_alert`)만 목킹하고 통째로 한 번 실행하는 테스트를
   추가했다. 시나리오: 보유 종목 하나가 손절선(-11%)을 넘어 매도되고, 동시에
   신규 후보 하나가 정량 필터(거래량 서지)를 통과해 분석(차트만 실제 의견 —
   뉴스·공시는 데이터 없음으로 자연 스킵, `degraded=True`) → 토론 → 매니저
   BUY 승인 → 게이트 통과 → 실주문까지 간다. `monkeypatch.chdir(tmp_path)`로
   모든 상대경로 로그(`logs/pipeline.jsonl`, `logs/trade_journal.jsonl`,
   `logs/portfolio_state.json`)를 격리했다 — 이 파일들의 기본 경로는 함수
   시그니처의 기본 인자값(정의 시점에 한 번 바인딩)이지만 **값 자체가 상대
   `Path` 객체**라 실제 파일 접근은 호출 시점의 cwd를 기준으로 풀리므로,
   `chdir`만으로 충분히 격리된다(경로 상수를 몽키패치할 필요가 없다 — 그건
   함수 기본값에 이미 구워져 있어 안 먹힌다). `llm.call_structured`는
   `response_model.__name__`으로 어떤 호출인지 구분해 응답하는 단일 가짜로
   대체했다 — `analysts.py`/`judgment.py`의 프롬프트 조립·재시도·스키마
   검증 로직은 전부 실제로 실행된다. 결과: 매매일지에 매도 1건+매수 1건,
   판단 로그에 정상 기록, 텔레그램 알림 2건이 통일된 양식 그대로 발송됨을
   확인 — 전부 정상.

세 파일 다 통과, 전체 스위트 241개 통과, 실제 로그 오염 없음 확인.

### 하루 파이프라인을 4단계로 분리 — A(판단)/B(집행)/C(1분 체크)/D(재량 매도 판단) (2026-08-11)

배포 첫날(2026-08-11 09:10) 실제로 크론이 돌다가 OOM으로 죽은 걸 SSH로 복구하며
확인하는 과정에서, 사용자가 기존 "하루 한 번(09:10) 판단+집행+매도평가"
구조 자체의 문제 세 가지를 지적했다:

1. 결정론적 손절/익절(`sell.evaluate_deterministic_sell`)이 하루 한 번만
   체크되면 그 사이(최대 24시간) 손실이 -10% 문턱을 훨씬 넘어갈 수 있다 —
   이전 프로젝트는 1분 간격으로 체크했다. 이 체크는 LLM 없이 KIS 시세 조회만
   하므로 1분 간격이어도 추가 비용이 없다(사용자 확인, KIS는 초당 제한만 있고
   이미 `kis.py`가 쓰로틀링함).
2. LLM 재량 매도가 장 시작 직후(09:10)에 돌면 개장 초반 변동성 때문에
   재평가 기준으로 나쁘다 — 장 마감 후가 하루 가격 흐름이 정리된 시점이라
   낫다.
3. 신규 매수 판단은 장이 열리기 전에 끝나 있어야 한다 — 장 시작 후 판단을
   시작하면(실제로 09:10에 시작해서 40분+ 걸렸고 OOM으로 완주도 못함) 판단
   근거가 이미 낡은 채로 집행하게 된다.

**최종 구조**: `07:00 A(decide_buys.py, 판단만) → 09:00 B(execute_open.py, 매도
먼저→매수 집행) → 09:00–15:30 매분 C(check_stop_loss.py, 결정론적 매도만) →
15:35 D(decide_llm_sell.py, LLM 재량 매도 판단만, 집행 안 함)`. LLM 재량 매도는
처음엔 장 마감 "직전"(15:10)에 판단+즉시집행을 같이 하는 안을 검토했으나,
그러면 LLM 호출 동안 `portfolio_state.json` 락을 D가 계속 쥐고 있어야 해서
그 사이 C(1분 체크)가 밀리는 문제가 있었다. 사용자 제안으로 "판단은 마감 후
(15:35), 집행은 다음 거래일 개장 직후 B가 신규 매수보다 먼저"로 바꿔서 이
락 경합 자체를 없앴다 — 매수/매도 둘 다 시장가 주문이라 집행 자체가 오래
안 걸리므로(초 단위) 하루 텀을 둬도 문제없다는 게 근거. 매도는 갭 체크 없이
그대로 집행한다(기존 원칙: 매도는 망설이지 않는다).

기존 함수(`pipeline.evaluate_holdings`, `pipeline.execute_buy_order`,
`sell.evaluate_deterministic_sell`)는 전혀 안 바꿨다 — "언제 부르느냐"만
바꾼 리팩터다. 새로 만든 것: `src/portfolio_store.py`(로드/원자적 저장/
`fcntl.flock` 락 — 이제 하루에 여러 프로세스가 `portfolio_state.json`을
건드리므로 필요해짐), `pipeline.finalize_sell`(매도 집행+로그+알림을
`evaluate_holdings`에서 뽑아내 즉시집행 경로와 지연집행 경로가 공유하게 함),
그리고 `logs/pending_buys.json`/`logs/pending_sells.json`(판단↔집행 사이를
잇는 파일 — 갭 체크·날짜 검증으로 근거가 낡았으면 무리하게 집행하지 않음).

`scripts/run_daily.py`는 크론에서 빠졌지만 로컬/수동 전체 파이프라인
테스트용으로 파일은 남겨뒀다.

**추가 (같은 날, 배포 직후)**: t3.small로 올린 뒤 EC2에서 `decide_buys.py`를
직접 한 번 완주시켜봤다 — 실제 소요시간 4분 29초(유니버스 199 -> 정량필터
통과 37 -> 분석·토론·매니저까지 전부 포함). 오늘 아침 OOM으로 죽기 전까지
40분+ 걸리던 것과 비교하면 훨씬 빠른데, 그날은 KIS 레이트리밋 재시도가 계속
걸린 영향이 컸던 것으로 보인다. 5분도 안 걸리는 작업에 07:00은 과한 여유라
장 시작(09:00) 기준 30분 버퍼만 남기고 **08:30**으로 당겼다(사용자 확정).

같은 실행에서 코스피200 유니버스가 200이 아니라 199개로 나온 것도 확인했는데,
이건 버그가 아니라 § "유니버스·시세 소스 재확정"에서 이미 정리한 대로다 —
코스피200은 리밸런싱·상장폐지·합병 등으로 조회 시점 구성종목 수가 정확히
200이 아닐 수 있고, `fetch_kospi200_universe`는 그 실제 값을 그대로 쓰지
강제로 200을 채우지 않는다.

### 노션 동기화가 4단계 분리 이후 크론에서 빠져 있던 버그 (2026-08-12)

사용자가 "노션에 기록은 언제 하는거야?"라고 물어서 확인하다가 발견: 위
"하루 파이프라인을 4단계로 분리"(2026-08-11) 리팩터 때 `_sync_notion` 호출을
`run_daily.py`에서 새 크론 스크립트로 옮기는 걸 빼먹었다. `run_daily.py`
자신은 그날 이후 크론에서 빠지고 로컬/수동 테스트용으로만 남았는데
(§ 위 항목), 노션 동기화는 그 안에만 있어서 실서비스 크론 경로에서는 하루도
안 빠짐없이 계속 스킵되고 있었다 — README에는 "노션 동기화 전부 연결 완료"로
적혀 있었지만 실제로는 배포 첫날부터 노션에 아무것도 안 올라가는 상태였다.

두 산출물의 자연스러운 위치가 서로 다르길래 한 곳이 아니라 갈라서 옮겼다:
- **매매일지**(`sync_trade_journal`, 이벤트 이력)는 `execute_open.py`(09:00,
  그날 매도·매수 집행 직후) 끝에 붙였다 — 이벤트가 실제로 `trade_journal.jsonl`에
  쓰이는 바로 그 시점이라 자연스럽다.
- **일일 리포트**(`sync_daily_report`)는 `decide_llm_sell.py`(15:35, 장마감 후)
  끝에 붙였다 — `_daily_report_children`이 만드는 문구 자체가 "장마감 기준
  보유 종목"이라, `check_stop_loss.py`가 09:00–15:30 매분 계속 포지션을 바꿀 수
  있는 `execute_open.py` 시점(09:00)에 만들면 라벨이 거짓말이 된다.
  `decide_llm_sell.py`는 그 시점 이후 실행되고 자기 자신은 포트폴리오 상태를
  안 바꾸므로(판단만 하고 집행은 다음날), 이 스크립트가 로드하는 portfolio가
  그날의 진짜 마지막 스냅샷이다.

`run_daily.py`의 `_sync_notion`(매매일지+리포트를 한 번에 호출)은 그대로
남겨뒀다 — 로컬에서 전체 파이프라인을 수동으로 한 번에 돌려볼 때는 두 산출물이
같은 시점(스크립트 종료 직후)에 나와도 문제없다.

### 일일 리포트 "오늘의 판단 요약"이 매일 "판단 로그가 없다"로 나오던 버그 (2026-08-13)

사용자가 어제·오늘 일일 리포트 모두 "오늘의 판단 요약"이 "판단 로그가 없다"로
비어 있다고 알려와서 확인. `decide_buys.py`(08:30 KST cron)가
`pipeline.run_daily`에 넘기는 `day`를 `datetime.now(timezone.utc)`로 만들고
있었다 — 08:30 KST는 UTC로는 전날 23:30이라, `run_day`가 `pipeline.jsonl`에
남기는 `"day"` 필드가 **항상 KST 거래일보다 하루 전** 날짜로 찍혔다.
`decide_llm_sell.py`가 15:35에 `notion_sync.sync_daily_report`를 호출할 때는
`today_kst`(정확한 KST 날짜)로 그날 판단을 필터링하므로, 하루씩 어긋나
`decisions_today`가 항상 빈 리스트였다 — 실제로는 매일 정상적으로 판단이
돌고 있었는데 리포트만 계속 빈 걸로 나온 것.

`execute_open.py`(09:00)·`check_stop_loss.py`(09:00–15:30)·`decide_llm_sell.py`
(15:35)는 전부 KST 09:00 이후에 도는 스크립트라 UTC 날짜와 KST 날짜가 우연히
일치해서 같은 버그가 없었다 — 오직 09:00 이전에 도는 `decide_buys.py`(그리고
로컬 수동 실행용 `run_daily.py`, 실행 시각에 따라 같은 함정)만 해당됐다.
고친 값은 `datetime.now(KST)`로 바꿨다 — `day`는 as_of 타임스탬프로도 쓰이는데
tz-aware KST 인스턴트는 UTC와 마찬가지로 다른 tz-aware 값과 정확히 비교되므로
분석가 쪽 동작에는 영향이 없다. 재발 방지로
`tests/test_decide_buys.py::test_run_daily_day_uses_kst_date_not_utc_date_at_0830_cron_time`
을 추가해 08:30 KST 시각을 고정하고 `day.date()`가 KST 거래일과 같은지 검증한다.

기존에 이미 "판단 로그가 없다"로 잘못 동기화된 날짜는 `logs/notion_daily_report_state.json`에
synced로 표시돼 있어 재실행해도 다시 안 만들어진다 — 과거 리포트를 바로잡으려면
그 상태 파일에서 해당 날짜 키를 지우고 수동으로 다시 돌려야 한다.

### 매매일지 총매수금액, 일일 리포트 금액 총정리 추가 (2026-08-13)

사용자 요청 두 가지를 위 버그 수정과 같이 반영:

1. **매매일지 "총매수금액"**: `_buy_row_properties`에 `entry_price * quantity`로
   계산한 값을 새 숫자 컬럼으로 추가(`create_trade_journal_database`에도 스키마
   반영). 이미 만들어진 노션 데이터베이스는 코드만 고친다고 컬럼이 안 생기므로
   실제 워크스페이스에 반영하려면 별도로 속성 추가(마이그레이션)가 필요하다.
2. **일일 리포트 "총정리"**: 리포트 마지막에 투자한 금액/남아있는 현금/총 금액을
   원화로 적는다. `PortfolioState`는 비중(weight)만 들고 절대 금액을 모르므로
   (§ 기술 스택 근처 주석과 동일한 이유 — 브로커가 유일한 절대 금액 출처),
   `decide_llm_sell.py`가 이미 그 시점에 KIS를 호출하는 김에
   `kis.fetch_account_balance()`(총평가금액)를 한 번 더 불러 `sync_daily_report`에
   `total_value`로 넘긴다. 조회 실패(`None`)해도 리포트 자체는 만들어지고 그
   절만 "조회 실패" 문구로 대체된다 — 노션 동기화는 부가 기능이라는 기존
   원칙과 동일.

### 일일 리포트 상세 내용을 승인된 매수만으로 축소, 판단 로그 한국어 번역 (2026-08-13)

같은 날 사용자 요청 두 가지 추가:

1. **일일 리포트 "오늘의 판단 요약" 축약**: 첫 줄 요약 문장(총 N개 판단·BUY
   승인 M개·게이트 거부 K개·나머지 HOLD)은 그대로 두고, 그 아래 종목별 상세
   불릿은 승인된 매수만 나열하도록 `_daily_report_children`을 바꿨다 — HOLD·
   거부 종목까지 전부 나열하면 유니버스 전체(200개 가까이) 판단이 매일 쌓여
   리포트가 지나치게 길어진다. 요약 문장은 여전히 `decisions_today` 전체
   기준이라 몇 개 중 몇 개가 승인/거부됐는지는 그대로 드러난다. 승인된 매수가
   0건인 날은 "오늘은 승인된 매수 없음" 문구로 대체(빈 섹션 방지).

2. **판단 로그 한국어 번역 (표시 계층에서만)**: 분석가·토론·매니저 프롬프트는
   전부 영어라(prompts/*.md) `decision.reason`, 토론 논거, LLM 재량매도
   `reasoning`이 전부 영어로 나온다. 사용자 확정: "토의·판단 자체는 영어로
   해도 상관없지만, 나한테 보여질 때(텔레그램 알림·노션 일지)는 한국어로
   번역해달라." 그래서 `logs/*.jsonl`에 남는 원문은 손대지 않고(프롬프트
   버전별 성능 추적의 원재료라 원문이 남아있어야 한다 — CLAUDE.md 핵심 계약의
   `evidence` 프롬프트 버전 태그와 같은 이유), 사람이 보는 표면을 만드는
   순간에만 번역한다.

   새 모듈 `src/translate.py`: `llm.call_structured`(기존 재시도·로깅 인프라
   그대로 재사용)로 짧은 번역 호출 하나(`_Translation{translated: str}`)를
   추가했다. **번역 실패는 원문을 그대로 반환한다**(예외를 삼킨다) — 번역은
   투자 판단이 아니라 표시 형식이라, 이것 때문에 텔레그램 알림이나 노션 동기화
   자체가 막히면 안 된다(노션 동기화 실패를 삼키는 기존 패턴과 동일 정신).

   번역을 호출하는 지점: `pipeline.execute_buy_order`(텔레그램 매수 알림),
   `pipeline.finalize_sell`(텔레그램 매도 알림, LLM 재량매도 reasoning이 있을
   때만), `notion_sync._buy_row_children`(매니저 최종 판단 + 토론 논거),
   `notion_sync._sell_row_children`(판단 사유), `notion_sync._daily_report_children`
   (승인된 매수 상세 불릿의 reason). 이 중 노션 쪽 함수들은 번역이 비동기
   호출이라 전부 `async def`로 바뀌었고, `notion_sync.sync_trade_journal`/
   `sync_daily_report`도 따라서 async가 됐다 — 호출부(`execute_open.py`의
   `_sync_trade_journal`, `decide_llm_sell.py`의 `_sync_daily_report`,
   `run_daily.py`의 `_sync_notion`)도 전부 `await`로 바꿨다.

   **함정과 수정**: pydantic의 `BaseModel.model_json_schema()`로 만든 스키마를
   그대로 `call_structured`에 넘겼더니 API가 400을 냈다(`additionalProperties`를
   object 타입에 명시적으로 `false`로 안 넣으면 거부됨) — `src/analysts.py`/
   `src/judgment.py`가 이미 스키마를 손으로 쓰는 이유가 바로 이거였는데
   놓쳤다. 손으로 쓴 스키마(`_TRANSLATION_RESPONSE_SCHEMA`)로 바꿔서 해결
   (사용자에게 실제 한 번 호출해 정상 번역되는 것까지 확인, 2026-08-13).
   이 버그가 있는 동안엔 번역 호출이 매번 조용히 실패해서 원문(영어)이 그대로
   노출되는 상태였다 — try/except가 실패를 삼키는 설계라 겉으로는 "그냥 항상
   영어로 나옴"으로만 보이고 에러가 안 드러났다. 앞으로 `call_structured`에
   새 응답 스키마를 추가할 때는 반드시 `additionalProperties: False`를
   손으로 넣을 것.

   **테스트 비용 주의**: 초기 구현 때 `tests/test_execute_buy_order.py`/
   `tests/test_evaluate_holdings.py`/`tests/test_end_to_end_workflow.py`가
   `translate.to_korean`을 안 막아서 테스트 스위트가 실제 Claude API를
   호출하고 있었다(스키마 버그로 400 응답이라 토큰 비용은 0이었지만, 목킹
   없이 네트워크를 타는 것 자체가 문제 — 사용자 방침: 테스트는 항상 목만
   쓴다). 관련 테스트 파일의 autouse fixture에 `translate.to_korean` 항등
   함수 목을 추가해서 막았다.

### 출구 규칙을 종목별로 — ExitPlan (2026-08-15 확정)

§5에서 확정했던 고정 문턱(-10% / +20% / 1-3씩 / -7%)을 **종목별로 진입 시점에
정하는 방식**으로 바꿨다.

**계기**: 사용자가 매매일지에서 "20% 익절한 건도 있고 14.x% 익절한 건도 있는데
왜 다른가"를 물었다. 답은 트레일링 2단계였지만(1차 익절 후 고점 대비 -7%라
실현률이 +11.6%부터 시작), 그 과정에서 진짜 문제가 드러났다 — **모든 종목에
같은 자를 대고 있었다.** 일간 변동성 1.2%짜리와 3.5%짜리에 똑같이 -10%를 걸면
앞쪽은 손절이 사실상 작동하지 않고 뒤쪽은 노이즈에 털린다.

**설계 논의**: 처음에 "조이는 방향으로만 허용"(코드 상수가 가장 느슨한 끝)을
제안했으나, 사용자가 **양방향 허용**을 선택했다. 대신 **진입 시 고정, 보유 중
재결정 없음**은 같이 확정했다.

이 조합이 안전한 이유는 위험한 건 자유도 자체가 아니라 **묻는 시점**이기
때문이다. 보유 중에 손절선을 물으면 이미 -8%인 포지션 앞에서 묻게 되고, 그러면
"지지선이 조금 아래", "실적 발표 앞둔 일시적 변동성" 같은 논거가 반드시 나온다.
모델이 나빠서가 아니라 물어보면 답을 만들어내기 때문이고 — 후보를 여러 개 주면
반드시 하나를 고르는 것(규칙 5)과 같은 성질이다. 문턱을 낮춘 적은 없는데 메커니즘이
대신 낮춰버리는, 이 프로젝트를 한 번 죽인 바로 그 모양이다. 아직 이해관계가 없는
진입 시점에 정하게 하고 그 뒤로 코드가 그대로 집행하면 이 경로가 아예 없다.

**확정 사항**:
- LLM이 내는 건 **손절폭 한 숫자뿐**이다. 익절선은 코드가 `2 x 손절폭`으로
  계산한다(2:1 손익비 강제, 사용자 확정). LLM이 자유롭게 정하는 숫자 개수를
  최소화하고, 손절을 넓혀도 익절 목표가 같이 멀어지게 만들어 "여유를 주는
  공짜 방법"이 되지 않게 하려는 것.
- 범위: 손절 3~15%, 익절 비중 15~60%, 트레일링 3~12%. 이건 "적정 수준" 판단이
  아니라 **파싱 사고 방지선**이다 — 범위 밖 값이 조용히 통과하면 항상 손절선이
  사라지는 쪽으로 틀린다. `ExitPlan`의 pydantic Field 제약과
  `judgment._exit_plan_from`의 클램핑에서 이중으로 막는다.

  **함정 — 응답 스키마의 number에는 minimum/maximum을 못 쓴다**: 처음엔
  `_MANAGER_RESPONSE_SCHEMA`의 number 필드에 min/max를 넣어 API 단에서도 범위를
  강제하려 했는데 400이 났다(`For 'number' type, properties maximum, minimum are
  not supported`, 2026-08-15 실호출로 확인). 위 `additionalProperties: False`
  함정과 같은 계열이다 — **`call_structured`에 새 스키마를 추가할 때는 JSON Schema
  전부가 지원되지 않는다고 가정하고 실제 호출로 한 번 확인할 것.** 지금은 범위를
  프롬프트 문구로만 알려주고 강제는 코드 클램핑이 한다. 어차피 구조화 출력이
  범위를 지킨다고 믿으면 안 되는 자리라 실질적 손해는 없다.
- 익절 비중 상한이 60%인 이유: 1.0이면 `(1-f)^n` 잔량 보존이 깨진다. 익절만으로는
  전량 청산되지 않는다는 §5의 성질을 유지한다.
- `degraded` 판단(분석가 일부 실패)은 LLM 계획을 버리고 고정 기본값으로 떨어진다.
  절반만 보고 있는 모델에게 손절선을 넓힐 재량까지 주지 않는다 — 게이트에서
  기준을 높이는 기존 원칙과 같은 방향.
- 추가매수는 기존 계획을 유지한다. 물타기하면서 손절선도 같이 넓히는 경로를
  열지 않기 위해서다.

**비용**: 추가 LLM 호출 0. `portfolio_manager` 응답에 필드 3개를 얹는 방식이라
호출 수가 그대로다.

**실호출 검증 (2026-08-15, 사용자 승인 후 1회)**: 합성 분석가 의견 + 합성 토론
논거로 `portfolio_manager`를 직접 불러(토론 단계를 건너뛰어 정확히 1회) 응답을
확인했다. 결과: `action=HOLD`(강세/약세가 팽팽한 입력이라 의도한 보수적 출력),
손절 5.5% → 익절 11.0%(2:1 성립), 익절 비중 30%, 트레일링 6% — 전부 범위 안이라
클램핑 없이 통과. 논거에 넣은 "최근 20일 일간 수익률 표준편차 1.4%"를 받아 손절을
약 4σ로 잡은 걸로 보아 "그 종목 자체의 변동성에서 손절을 정하라"는 프롬프트 지시가
실제로 반영된다. 1901 in / 168 out 토큰, 1회 시도, 5.3초.

아직 검증 안 된 것: 실제 매수가 승인된 날 `ExitPlan`이 진짜 포지션에 박혀 손절/익절이
그 값으로 발동하는지. 이건 개장일(8/17 월요일은 광복절 대체공휴일이라 휴장, 다음
개장일은 8/18 화요일)에 **매수가 실제로 나야** 확인되는데, 이 시스템은 매수 없음이
정상 출력이라 날짜를 못 박을 수 없다. 첫 실거래 포지션이 생기면 `logs/trade_journal.jsonl`의
`exit_plan` 필드부터 확인할 것.

**측정용으로 남긴 것**: 매수·매도 로그 양쪽에 실제 적용된 `exit_plan`을 기록한다
(`None`이면 고정 기본값). LLM이 정한 출구가 상수보다 나았는지를 나중에 갈라볼 수
있어야 하기 때문이다. 다만 "고정값이었다면 어디서 잘렸을지"의 완전한 반사실
계산은 가격 경로 리플레이가 필요해서 별도 오프라인 분석으로 남겼다 — 매도 시점에
한 점만 보고는 알 수 없다.

**같이 고친 것 — 주식수 내림과 비중 불일치**: `execute_sell_order`가 요청 비율
(`sell_fraction`)로 `weight`를 깎으면서 주식수는 `int(quantity * fraction)`으로
내림하고 있었다. 4주 보유 중 1/3 익절이면 실제로는 1주(25%)만 나가는데 장부
비중은 33.3% 줄어 실제 보유보다 작아진다. 실제 체결 수량 비율로 비중을 깎도록
바꿨다. 이걸 고치지 않으면 아래 매매일지의 "줄인 비중"이 실제와 안 맞는다.
(주식수 자체는 비율 재계산에 맡기지 않고 체결 수량으로 덮어쓴다 — 3주 중 1주일
때 `int(3 * (1/3))`이 부동소수 오차로 0이 된다.)

**매매일지 추가 항목 (사용자 요청)**: 매도 로그와 노션에 `portfolio_weight_sold`
(전체 대비 줄인 비중), `portfolio_weight_after`(잔여 비중), `shares_sold`,
`sell_amount`(매도 금액)를 남긴다. 부분 익절은 `sell_fraction`이 "잔량 대비"
비율이라 그것만 봐서는 포트폴리오를 얼마나 줄였는지 안 보인다. 노션 매매일지
DB에 `매도금액`/`줄인비중`/`잔여비중` 속성이 추가됐고, 일일 리포트 매도 불릿에도
같이 찍힌다. 이 기능 이전에 쌓인 매도 로그엔 이 필드들이 없어서 노션 동기화는
없으면 그냥 비운다.

### 진입가가 실제 체결가와 어긋나 익절이 오발동한 건 (2026-08-15 발견·수정)

매매일지에 새 필드를 소급 입력하려고 브로커 체결 내역과 대조하다가 발견했다.
**소급 입력보다 이게 훨씬 중요한 문제였다.**

**증상**: 192820(코스맥스)의 일지 진입가가 210,000원인데 실제 체결단가는
232,000원이었다(+10.5% 차이). 시스템은 210,000을 기준으로 계산했으므로
247,300원을 "+20% 도달"로 보고 익절을 발동했지만, 실제 원가 기준으로는
**+6.6%**였다. 2차 트레일링 익절도 일지엔 +14.52%지만 실제로는 +4.3%다.

전 종목 대조 결과 003550·036570은 정확히 일치, 282330(-0.13%)·009240(+0.26%)은
오차 수준, 051900(-1.43%)과 192820(+10.5%)이 어긋났다.

**원인**: `execute_buy_order`가 `entry_price = fill_price if fill_price is not None
else current_price`로, 체결가 조회 실패 시 **주문 직전 호가**로 폴백했다. 시장가
주문이라 호가와 체결가는 원래 다를 수 있는데, 그 오차가 포지션 수명 내내 손절·익절
기준으로 남는다. 진입가가 낮게 기록되면 **익절은 일찍 터지고 손절은 늦게 터진다** —
안전장치가 한쪽으로 기운다.

`fetch_fill_price` 자체에도 버그가 있었다. `SLL_BUY_DVSN_CD="00"`(전체)이라 같은 날
같은 종목에 매수와 매도가 모두 있으면 output2가 둘을 **한데 섞어** 평균을 낸다.
192820의 8/12(매수 38주 + 매도 20주)를 이걸로 조회하면 237,711원이 나온다 —
진입가로 쓰면 안 되는 값이다.

**수정**:
- `fetch_fill_price`: `SLL_BUY_DVSN_CD="02"`(매수만).
- `kis.fetch_position_avg_price` 신설 — 잔고조회 output1의 매입평균가. 체결 직후라
  일별체결 집계에 아직 안 잡힌 경우의 2차 출처다(방금 산 종목이라 보유분 평균가 =
  이 주문의 체결가).
- 진입가 출처를 체인으로: 체결가 → 잔고 매입평균가 → (둘 다 실패 시) 호가.
  호가로 밀린 경우 `logger.error`와 매매일지 `entry_price_source="quote_fallback"`
  양쪽에 남긴다. 포지션을 리스크 관리에서 빼지 않되(entry_price=None이면 매도 평가
  자체가 스킵된다), 기준이 실제 원가와 다를 수 있다는 걸 조용히 넘기지 않는다.
- `_kst_today()` 신설 — 체결 조회 주문일자를 UTC가 아닌 KST로. 장중엔 두 날짜가
  같아 실제 버그는 아니었지만, KRX 주문일자는 KST 개념이고 이 프로젝트는 이미
  UTC 날짜를 그대로 써서 한 번 당했다(커밋 832fb8b).

**아직 안 고친 것 — 기존 보유분의 진입가**: 지금 들고 있는 192820(210,000 기록 /
232,000 실제), 051900(314,000 / 309,500), 282330(150,500 / 150,300)은 여전히 틀린
원가로 손절·익절이 판정된다. 특히 192820은 10% 차이라 남은 12주도 같은 오발동
위험이 있다. 브로커 매입평균가로 교정하려면 EC2의 `portfolio.json`을 직접 고쳐야
해서 사용자 판단으로 남겨뒀다.

**교훈**: 브로커가 사실의 출처다. 시스템이 기록한 값과 브로커가 보고하는 값이
다를 수 있고, 다르면 항상 브로커가 맞다. 매매일지 숫자를 신뢰하기 전에 잔고·체결
내역과 대조할 것.

### 매매일지 소급 입력 (2026-08-15)

새로 추가한 필드(수량/매도금액/줄인비중/잔여비중)를 기존 매도 3건에 채웠다.
원칙은 **확정 가능한 것만 쓰고 추정으로 메우지 않는다**. 이 프로젝트가 측정
가능성 때문에 존재하는데, 틀린 값에 정확해 보이는 외양을 입히는 게 제일 나쁘다.

- 009240 8/13 손절: 189주 / 7,199,050원 — 브로커 확정치(그날 단독 매도).
- 192820 8/12 1차 익절 12주, 2차 8주 — 수량은 결정론적 규칙 `int(잔량/3)`으로
  확정된다(38 → 12 → 8 → 6, 잔여 12주가 증권사 실제 잔고와 일치해 체인 전체가
  검증됨). **금액은 비워뒀다** — 브로커가 8/12 매도 2건을 20주/4,946,000원으로
  합산 보고해 건별 분리가 불가능하다.
- 비중은 `TRADE_WEIGHT=0.08`과 당시 매도 로직에서 계산.
- 각 행에 출처와 한계를 주석 블록으로 남겼다. 실현손익률이 사실과 다른 두 행
  (192820)에는 실제값과 원인도 같이 적었다 — 숫자만 고치면 왜 틀렸는지가 사라진다.

**8/14 매도 6주(1,451,500원)는 아직 노션에 없다.** 유실이 아니라 8/15가 휴장이라
싱크 크론이 안 돈 것이다. 다음 개장일(8/18) 싱크에서 별도 행으로 올라온다.

### 매매일지는 호가가 아니라 체결 원본으로 쓴다 (2026-08-15 확정)

사용자 지적: **시장가로 주문하니 판단 시점 값과 실제 체결이 다르다. 일지는 실제
매수/매도 기록을 확인하고 써야 한다.** 위 진입가 버그가 매수 쪽 증상이었다면,
이건 그 일반형이다 — 매도 쪽은 아직 호가를 적고 있었다.

**고치기 전 상태**: `finalize_sell`이 `exit_price = current_price`(판단 시점 호가)를
적었고, `realized_pnl_pct`와 `sell_amount`가 전부 거기서 계산됐다. 즉 일지의
손익률·매도금액이 실제 체결과 무관한 값이었다.

**핵심 설계 — 체결은 주문을 낸 함수만 정확히 잴 수 있다**: 집계를 사후에 한 번만
조회하면 안 된다. KIS의 일별체결 output2는 그날 전체를 합산하므로 같은 종목을 같은
날 두 번 매도하면 두 건이 섞인다(192820이 실제로 12주·8주 → 20주/4,946,000원으로
합산 보고돼 건별 분리가 불가능했다). 그래서 **주문 직전·직후의 누적 체결 집계를
사이에 두고 차를 낸다**(`kis.fetch_daily_fill_totals` + `kis.fill_between`).
이건 주문을 내는 함수 안에서만 가능하므로, `SellExecuteFn`이 `PortfolioState`가
아니라 `(PortfolioState, FillRecord | None)`을 반환하도록 계약을 바꿨다.

**`FillRecord`는 수량과 총액만 들고 단가는 계산 프로퍼티**로 뒀다 — 부분 체결이
여러 단가로 나뉘어도 가중평균이 자동으로 맞는다. 총액도 브로커 원본을 그대로
쓴다(수량 × 단가로 되계산하면 어긋난다).

**체결을 확인 못 하면 지어내지 않는다.** `fill_between`은 조회 실패나 수량 미증가
시 `None`이고, 시뮬레이션 경로(`execute_sell_simulated`)는 **항상** `None`이다 —
실주문을 낸 적이 없으니 체결이라는 사실 자체가 없다. 호출부는 호가로 폴백하되
`exit_price_source="quote_fallback"`로 남긴다. 판단 시점 호가도
`decision_price`로 계속 남겨 슬리피지를 추적할 수 있게 했다.

체결가는 일지뿐 아니라 **상태에도** 반영된다 — 부분 익절 후 `peak_price` 리셋과
비중 축소가 전부 체결가 기준이다. 호가로 리셋하면 이후 트레일링 단계가 전부
어긋난 기준으로 판정된다.

매수 쪽도 같은 브래킷을 적용해 진입가 출처 체인을 4단으로 정리했다:
`fill`(전후 집계 차, 이 주문 하나) → `daily_avg`(그날 매수 집계 평균, 추가매수와
섞일 수 있음) → `position_avg`(잔고 매입평균가) → `quote_fallback`(호가).

**테스트 함정 (또 겪음)**: `fetch_daily_fill_totals`를 목킹 안 한 테스트들이 실제
KIS를 때려서 스위트가 1.3초 → 43초가 됐다. 타임아웃까지 기다리느라 느려진 것이라
실패로는 안 드러난다. `test_sell.py`/`test_evaluate_holdings.py`/
`test_execute_buy_order.py`에 autouse 픽스처로 막았다. **KIS/LLM을 새로 호출하는
코드를 추가하면 관련 테스트 파일의 autouse 픽스처부터 확인할 것** — 스위트
실행시간이 갑자기 늘면 네트워크가 새는 신호다.

`test_end_to_end_workflow.py`는 호가와 체결가를 일부러 다르게 목킹해(매수 호가
70,000/체결 70,500, 매도 호가 89/체결 88) 일지에 체결가가 적히는지 끝까지
확인한다 — 호가가 새면 여기서 걸린다.

### 브로커 잔고 대조 — src/reconcile.py (2026-08-15)

진입가 버그를 고쳐도 **이미 어긋난 채 들고 있는 포지션**은 계속 틀린 기준으로
손절·익절이 판정된다. 그걸 잡는 모듈을 따로 뒀다.

손으로 `portfolio_state.json`을 고치지 않은 이유: 이 건에서 이미 손계산이 한 번
틀렸다(192820 잔여 주식수를 18주로 계산했는데 실제는 12주였다 — 같은 날 두 번
익절된 걸 놓쳤다). 브로커를 직접 읽어 맞추는 코드는 그런 실수를 할 수 없고,
드리프트가 또 생겨도 다시 쓸 수 있다.

- `kis.fetch_holdings()` — 보유 종목 전체 `{티커: (수량, 매입평균가)}`.
  `fetch_position_avg_price`도 이걸 쓰도록 바꿨다.
- `reconcile.reconcile(portfolio, holdings)` — 순수 함수. 네트워크·파일 안 건드려서
  실계좌 없이 전부 테스트된다(`tests/test_reconcile.py`).
- `scripts/reconcile_portfolio.py` — 기본은 드라이런, `--apply`로 교정.

**교정하는 것**: `entry_price`, `quantity`. 진입가 교정이 고점을 추월하면
`peak_price`도 같이 올린다(진입가보다 낮은 고점은 성립하지 않고, 그대로 두면
트레일링이 즉시 발동한다).

**교정하지 않는 것**:
- `weight` — 브로커엔 "포트폴리오 비중" 개념이 없다. 이 필드는 매수 시점 원가 기준
  비중이고 시세로 재평가되지 않아 시장가치 비중과 원래 다르다. 이 버그와 무관한
  설계 사안이라 조용히 바꾸지 않는다.
- 브로커에 없는 포지션 — 보고만 하고 **지우지 않는다**. 조회가 부분 실패했을 수도
  있고, 포지션을 자동으로 없애면 손절 대상이 조용히 사라진다.

**장중 `--apply` 금지**: 1분마다 도는 `check_stop_loss.py`와 같은 상태 파일을 놓고
경쟁한다. 락 덕에 깨지진 않지만 교정 직후 손절선이 바뀌어 그 판정이 어느 값
기준이었는지 헷갈린다. 장 마감 후에 돌릴 것.

### 매도 비중은 그 종목 보유분 100% 기준으로 (2026-08-15 확정)

사용자 지적: **"잔여/줄인 비중을 전체 포트폴리오 기준으로 쓰니 무슨 말인지 모르겠다.
종목별 100% 기준으로 써야 이해가 된다. 이걸 위해 작성하라고 한 것이다."**

맞는 지적이고, 목적을 놓친 건 이쪽이었다. 매매일지는 **사람이 읽으라고** 쓰는
것인데, 부분 익절을 "포트폴리오 비중 1.19% 축소"로 적으면 읽는 사람이 해석할 수도
검산할 수도 없다. 정작 알고 싶은 건 "이 종목에서 얼마나 팔았고 얼마나 남았나"다.

- `position_fraction_sold` / `position_fraction_remaining` — 이 종목 보유분을
  100%로 놓은 비율. **합이 항상 1.0**이라 한 행만 보고도 해석된다.
- `shares_before` / `shares_after` — 퍼센트를 주식수로 검산할 수 있게 같이 남긴다.
  주식수 내림 때문에 1/3이 정확히 33.3%가 아닌 경우가 흔하다(31주면 10주=32.3%).
- 포트폴리오 대비 값(`portfolio_weight_*`)은 로그엔 계속 남기되 노션엔 안 띄운다.
- 노션 컬럼: `줄인비중` 삭제, `매도비중`·`잔여수량` 추가.

**기존 기록 재작성**: 매도 4건을 새 기준으로 다시 채웠다. 코스맥스 매도금액을
비워뒀던 것도 채웠다 — 브로커가 8/12 두 건을 20주/4,946,000원으로 합산 보고해
건별 체결액을 직접 못 얻으므로, `(주식수 x 판단가)` 비율로 안분하되 **두 몫의 합이
브로커 총액과 정확히 일치**하도록 둘째를 잔액으로 뒀다(오차는 총액 대비 0.04%).
안분한 행은 `sell_amount_source="allocated"`로 구분된다. 비워두는 것보다 낫다는
사용자 판단이다.

재작성 결과 체인이 실제 잔고까지 끊김 없이 이어지는 것을 검증했다:

```
192820  38주 -> 26주 (31.6% 매도, 3,022,778원, +8.58%)
        26주 -> 18주 (30.8% 매도, 1,923,222원, +3.62%)
        18주 -> 12주 (33.3% 매도, 1,451,500원, +4.27%)
        최종 12주 = 브로커 12주 = 상태파일 12주
009240 189주 ->  0주 (100%  매도, 7,199,050원, -10.18%)
```

실현손익률도 실제 원가 기준으로 다시 계산했다. 이전에 +20.0%/+14.52%로 적혀
있던 두 건은 틀린 진입가(210,000) 때문이었고 실제로는 +8.58%/+3.62%다.

**소급 작업 중 저지른 실수 (기록용)**: 노션 페이지를 `(티커, 일자)`로 찾는 스크립트를
썼는데, 같은 날 같은 종목 매도가 2건이라 `next()`가 둘 다 같은 페이지를 가리켜
한 행이 다른 행을 덮어썼다. 같은 날 같은 종목이 여러 번 거래되는 건 이 시스템에서
정상이므로(트레일링 익절), **날짜+티커는 키가 될 수 없다.** 페이지 ID로 1:1 배정해
바로잡았다. `notion_sync`의 dedup 키가 같은 이유로 이미 한 번 고쳐진 적 있다
(커밋 `ca7a25e`) — 같은 함정을 두 번째로 밟았다.
