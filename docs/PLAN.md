# 설계 배경과 근거

`CLAUDE.md`의 규칙들이 왜 그렇게 정해졌는지를 담은 문서.
규칙을 바꾸고 싶어질 때 여기를 먼저 읽을 것.

---

## 1. 이전 프로젝트의 실패

### 무엇이 있었나

한투 API + AWS EC2 + MySQL 기반 자동매매 시스템. 정량·기술적 지표로 후보를 거른 뒤
남은 종목의 데이터를 차트 이미지로 변환하고, Claude가 이미지를 분석해 신뢰도 점수를
매겨 문턱을 넘으면 매수하는 구조였다. 모의투자에서 약 10% 수익이 나왔다.

### 무엇이 문제였나

수익이 지속되지 않았고, **매수하면 안 되는 상황에서도 매수가 발생했다.**

구조적 원인은 스케줄러에 있었다. 15:35 장 마감 후부터 18~24시 매시 정각에,
pending 신호가 5개 미만이면 `pre_market_setup(is_retry=True)`를 재실행하는 로직이
있었다. 의도는 "분석이 덜 끝났으면 마저 하자"였지만, 실제 작동은 "5개를 채울 때까지
계속 돌린다"였다.

같은 후보를 반복해서 LLM에게 보여주면 언젠가는 통과한다. 문턱값을 낮춘 코드는 어디에도
없지만, **재시도 자체가 문턱을 낮추는 역할을 했다.**

### 왜 이게 치명적이었나

매일 매수가 강제되면 신호의 예측력을 측정할 수 없다. 어떤 매수가 "신호가 좋아서"이고
어떤 게 "할당량을 채워야 해서"인지 사후에 구분할 방법이 없기 때문이다.

그래서 "수익이 안 났다"와 "무리하게 샀다"는 별개 문제가 아니다.
**후자가 전자의 원인 진단을 불가능하게 만든 관계다.**

모의투자 10% 수익도 마찬가지로 해석 불가다. IC 같은 지표로 유의성을 확인하지 않았기
때문에, 몇 개 종목이 우연히 터진 결과일 가능성을 배제할 수 없다.

### 코드를 재사용하지 않는 이유

두 가지다. 하나는 위 결함이 스케줄링·재시도·상태 복원 로직 전반에 얽혀 있어서
부분 수정으로 걷어내기 어렵다는 것. 다른 하나는 그냥 다시 손대고 싶지 않다는 것이고,
이건 충분한 이유다. 사이드 프로젝트는 의욕이 연료다.

가져오는 것은 **워크플로우 지식**뿐이다. 휴장일 처리, 장 마감 후 분석 → 다음날 개장
매수 흐름, EC2 재기동 시 캐치업 같은 운영 노하우는 두 번째 구현에서 훨씬 빠르게 나온다.

## 2. 계층 설계의 근거

### 수집은 에이전트가 아니다

뉴스 크롤링, DART 조회, 시세 fetch는 전부 결정론적 ETL이다. 여기에 LLM을 붙이면
비용과 레이턴시만 늘고 재현성이 깨진다. LLM 호출은 판단이 필요한 지점에만 넣는다.

### 왜 강세/약세 토론 단계가 있나

LLM은 주어진 근거에 동조하는 편향이 강하다. 분석가들의 의견을 그대로 종합하면
긍정 방향으로 쏠린다. 반대 논거를 **명시적으로 생성하게 강제**해야 균형이 잡힌다.

### 에이전트 합의는 신뢰의 근거가 아니다

같은 base model 5개가 동의하는 것은 독립 표본 5개가 아니라 상관된 오류 1개다.
진짜 다양성은 모델이 아니라 **데이터 소스**에서 나온다. 차트만 보는 분석가와 공시만
보는 분석가가 다른 결론을 내는 건 의미가 있지만, 같은 뉴스를 두 번 읽히는 건 의미가 없다.

이것이 분석가를 데이터 소스 기준으로 나눈 이유다.

### 왜 리스크 게이트가 LLM이 아닌가

종목당 최대 비중, 섹터 집중도, 일일 최대 손실, 총 노출은 "판단"의 영역이 아니라
넘으면 무조건 거부하는 하드 룰이다. LLM에게는 거부권만 주고 승인권은 주지 않는다.

### 비용 구조

KOSPI200 전체에 분석가 4개를 돌리면 하루 800회 호출이다. 정량 필터로 후보를
10~20개로 줄인 뒤에 LLM을 투입하는 순서를 유지한다.

종목당 독립 호출(비교 금지) 원칙 때문에 호출 수가 늘지만, 무리한 매수를 막는 가장
효과적인 장치라 이 비용은 감수한다.

## 3. 측정에 대해

### 왜 백테스트 수익률을 믿으면 안 되나

정량 모델의 룩어헤드 편향은 코드로 막을 수 있다. 하지만 LLM은 2024년 뉴스를 읽으면
그 뒤에 주가가 어떻게 됐는지 이미 학습해서 알고 있고, 이건 모델 가중치 안에 있어서
막을 방법이 없다.

**LLM 컴포넌트가 들어간 시스템의 과거 구간 백테스트 수치는 참고용으로도 위험하다.**
워크포워드 또는 실시간 모의투자로만 검증한다.

### 왜 IC인가

IC(information coefficient)는 예측값과 실제 수익률의 순위상관이다.
0.03~0.05만 안정적으로 나와도 쓸 만한 신호다.

수익률부터 보면 몇 개 종목이 우연히 터진 것을 실력으로 착각하게 된다. IC를 먼저 보면
"신호가 전반적으로 방향을 맞히고 있는가"를 종목 수 전체에 걸쳐 확인할 수 있다.

---

## 4. 빅데이터 예측 모델에 대한 판단

### 왜 지금 넣지 않나

"데이터를 더 많이 넣으면 예측이 좋아진다"는 가정은 주식에서 잘 성립하지 않는다.
금융 시계열은 신호 대 잡음비가 극단적으로 낮아서, 데이터를 10배로 늘려도 모델이
학습하는 건 대부분 잡음이다. 시장 구조가 바뀌기 때문에 오래된 데이터는 오히려 해롭다.

규모 감각도 필요하다. KOSPI200 × 10년 일봉은 약 50만 행으로, 노트북 pandas에서 도는
크기지 빅데이터가 아니다. 진짜 빅데이터가 되려면 틱·호가창 레벨로 내려가야 하는데,
그 순간 인프라 비용이 급증하고 얻는 알파는 개인이 접근하기 어려운 초단타 영역이다.

그리고 더 근본적으로 — 이전 실패의 원인이 "예측력 부족"이 아니라 "문턱 부재"였다면,
아무리 좋은 모델을 넣어도 성능이 측정되지 않는다. 순서를 지켜야 한다.

### 넣게 된다면

가격 방향 이진 분류는 승률 52~53%가 현실적 천장이고 거래비용 빼면 남는 게 없다.
대신 이런 타깃이 낫다:

| 타깃 | 근거 |
|---|---|
| 횡단면 랭킹 (오늘 200종목 중 상대 순위) | 시장 방향을 맞힐 필요가 없어짐. 노이즈가 적음 |
| 변동성 예측 | 실제로 예측 가능성이 높은 몇 안 되는 영역. 포지션 사이징에 직접 쓰임 |
| 이벤트 후 이상수익률 | 공시 분석가와 직결. 라벨링이 명확하고 이벤트 스터디로 검증 가능 |

구조상으로는 별도 에이전트가 아니라 `agent="quant"` 분석가로 붙인다.
이때 `confidence`는 모델의 예측 확률이 아니라 **최근 60일 롤링 IC**로 잡는다.
모델은 틀리고 있을 때도 높은 확률을 뱉기 때문에, 최근 예측력이 무너지면 자동으로
발언권이 줄어들게 만들어야 한다.

### 리스크 게이트 수치 (2026-08-08 확정)

| 룰 | 값 | rejected_by |
|---|---|---|
| 종목당 최대 비중 | 15% | `position_limit` |
| 섹터 집중도 한도 | 40% | `sector_concentration` |

| 총 노출 한도 | 100% (개별 종목·섹터 한도로만 통제, 별도 상한 없음) | — |

마일스톤 1의 게이트 구현은 이 수치를 하드코딩된 상수가 아니라 설정값으로 분리해
나중에 백테스트/튜닝 시 코드 수정 없이 바꿀 수 있게 한다.

### 차트 분석가 입력 형태·시세 데이터 소스 (2026-08-08 확정)

- **입력 형태**: 이미지+vision이 아니라 텍스트(OHLCV + 파생 지표 수치)로 먼저
  시도한다. 차트 이미지를 보고 판단하는 것과 동등한 효과를 노리고 지표를
  추세(SMA)·모멘텀(RSI)·거래량·지지저항(최근 고가/저가)까지 커버하도록 구성.
  텍스트로 부족하다고 판단되면 그때 이미지+vision으로 전환한다 — 지금 미리
  만들지 않는다.
- **시세 데이터**: pykrx(무료, 인증 불필요) 대신 **네이버 금융 비공식 차트 API
  스크래핑**을 쓴다. pykrx의 실시간성이 부족하다고 판단해서 사용자가 직접 선택.
  비공식 엔드포인트라 구조가 바뀔 수 있음 — `collectors.py`의 수집 실패는 데이터
  수집 실패 경로로만 재시도한다 (규칙 4).

### 뉴스 분석가 데이터 소스 (2026-08-08 확정)

- **종목 뉴스**: `finance.naver.com/item/news_news.naver?code=<종목코드>` — 네이버가
  이미 종목코드로 정확히 매핑해주는 페이지라 우리 쪽에서 회사명 키워드 매칭을 할
  필요가 없다. **`Referer: finance.naver.com/item/news.naver?code=...` 헤더가
  없으면 빈 결과만 온다** — 이 헤더는 필수다.
- **업종(도메인) 뉴스**: 네이버에 종목처럼 깔끔한 업종별 뉴스 탭이 없다 (업종 상세
  페이지에도 없음, 자체 뉴스검색 기능은 테스트해보니 사실상 죽어 있음 — 항상 0건).
  대신 `finance.naver.com/news/` 전체 시황 허브를 긁어 헤드라인 중 업종명이 포함된
  것만 골라낸다. 회사명 매칭보다 오탐 허용 범위가 넓은 업종 단위라 키워드 매칭이
  실용적으로 괜찮다고 판단. 개별 기사 타임스탬프는 이 페이지에 없다.
- **뉴스 분석가 프롬프트 설계**: 종목 뉴스가 메인 판단 대상, 업종 뉴스는 "이 종목이
  속한 시장 배경" 참고용으로 명확히 구분해서 준다 — 종목 간 비교가 아니라 이 종목
  하나를 둘러싼 맥락이라 규칙 5(종목 비교 금지) 위반이 아니다.
- **개발 중 API 사용 원칙 (사용자 피드백, 2026-08-08)**: 개발·테스트 단계에서는
  Claude API를 실제로 호출하지 않는다 — 모든 자동 테스트는 모킹으로만 돈다. 실제
  API 확인은 `tests/test_live_smoke.py`에 최소 규모(종목 1개)로만 두고, 기본적으로
  스킵된다. 종목 여러 개 × 여러 날 규모의 실측정(`tests/test_live_signal_rate.py`
  같은)은 사용자가 명시적으로 요청하고 비용 규모를 먼저 확인했을 때만 실행한다.

### 공시 분석가 데이터 소스 (2026-08-08 확정)

- **DART(전자공시시스템) Open API**를 그대로 쓴다 — 차트·뉴스처럼 네이버를
  리버스엔지니어링할 필요 없이 금융감독원 공식 API가 있다. `DART_API_KEY`
  환경변수 필요(무료 발급, opendart.fss.or.kr).
- 두 엔드포인트 조합: (1) `corpCode.xml` — 전체 법인의 종목코드↔고유번호(corp_code)
  매핑을 ZIP으로 한 번에 받아 프로세스 생애주기 동안 메모리 캐시(자주 안 바뀌는
  데이터라 파일 캐시까지는 불필요), (2) `list.json` — corp_code로 종목별 공시 목록
  조회. **corp_code 없이 조회하면 전체 법인 대상 검색이 되어 종목당 독립 호출
  원칙(규칙 5)이 깨지므로 항상 corp_code를 채워서 요청한다.**
- `status="013"`(조회된 데이터 없음)은 에러가 아니라 정상적인 0건 상태로 처리 —
  뉴스 수집기의 "0건 vs 수집 실패" 구분과 동일한 패턴.
- **공시 원문(본문)은 가져오지 않는다** — 보고서명(`report_nm`) 자체가 한국 공시
  특성상 정보 밀도가 높아 뉴스 분석가와 같은 스코프(헤드라인/제목만)로 맞췄다.
  원문 크롤링은 나중에 필요성이 확인되면 추가.

### 마일스톤 3 착수 — IC 측정은 인프라만, 오늘 숫자는 안 나온다 (2026-08-08)

차트·뉴스·공시 세 분석가가 다 붙어서 §3(측정) 단계로 넘어갔다. 여기서 중요한 제약을
다시 확인함: **오늘 당장 IC를 계산할 수 없다.** IC는 (그날 예측 점수, 그 이후 실현
수익률)의 순위상관인데, 뉴스·공시 수집기는 "오늘 시점" 데이터만 긁어오지 과거 특정
날짜의 스냅샷을 재구성하지 못한다 — 그리고 설사 됐다 해도 §3이 이미 명시한 대로
LLM 컴포넌트에는 백테스트 대신 워크포워드·실시간 모의투자만 쓰라고 못 박혀 있다.

그래서 이번에 만든 건 **인프라**뿐이다 (`src/evaluation.py`):
- `information_coefficient(pairs)` — 스피어만 순위상관, 순수 파이썬(외부 의존성 없음).
- `compute_forward_return(ticker, as_of, forward_days)` — 차트 수집기(무료)로 실현
  수익률 계산. `as_of` 이후 데이터가 아직 없으면 None — 이게 "시간이 지나야 한다"는
  제약이 코드로 드러나는 지점이다.
- `summarize_ic(log_path, forward_days)` — 로그에 쌓인 예측과 실현 수익률로 일별
  횡단면 IC의 평균·표준편차 계산.

실제로 IC 숫자를 얻으려면: 앞으로 매일 파이프라인을 실제로 돌려 `logs/pipeline.jsonl`
(임시 tmp_path 말고 진짜 경로)에 예측을 쌓고, 며칠~몇 주 뒤 `summarize_ic`를 돌린다.
`run_day`가 남기는 로그에는 이제 `avg_score`/`avg_confidence`가 필드로 들어간다
(전에는 `Decision.reason` 문자열 안에만 있었음).

### 판단 계층 구현 — 강세/약세 토론 + 포트폴리오 매니저 (2026-08-08 확정)

`pipeline.propose_decision()`(평균 점수 ≥0.85 문턱)이 임시로 대신하던 "판단: LLM"
계층을 실제로 구현했다 (`src/judgment.py`). 구조: 종목 하나의 분석가 의견을 받아
강세 논거·약세 논거를 **서로의 출력을 못 보게 독립적으로** 생성(`asyncio.gather`)한
뒤, 포트폴리오 매니저가 분석가 의견+양쪽 논거를 종합해 BUY/HOLD를 최종 판단한다.

- **왜 두 방향을 강제로 생성하는가** (docs/PLAN.md §2): LLM은 주어진 근거에 동조하는
  편향이 있다. 강세/약세를 데이터가 한쪽으로 쏠려 있어도 억지로 둘 다 만들게 해서
  균형을 잡는다.
- **규칙 6과의 관계**: 매니저가 BUY를 직접 말해도 규칙 위반이 아니다 — 그건 추천일
  뿐, 그 뒤 리스크 게이트(코드)가 최종 승인권을 갖는다. 매니저의 HOLD는 그대로
  확정(매수 없음)되고 매니저의 BUY는 게이트가 거부할 수 있다는 게 "LLM은 거부권만
  가진다"의 실질적 구현이다.
- **`AnalystOpinion`은 안 건드렸다.** CLAUDE.md가 준 고정 계약(score/confidence/
  evidence만, reasoning 텍스트 없음)이라 토론 단계는 각 분석가의 숫자 패턴만 보고
  논거를 만든다 — 원문 reasoning까지 주려면 계약을 바꿔야 해서 안 했다. 대신 새로
  만든 `DebateArgument`(자유 설계 가능한 신규 타입)와 `Decision.debate`/
  `Decision.evidence`(감사 추적용, 기본값 있는 optional 필드)는 추가했다.
- `pipeline.run_day()`가 `judge_fn` 파라미터를 요구하도록 바뀌었다 — 기본값 없음,
  호출부가 항상 명시적으로 골라야 한다. 비용 없는 더미/측정용은
  `pipeline.propose_decision`(그대로 유지, 삭제 안 함), 실제 판단은
  `judgment.judge`.

- **코스피200 실제 구성종목 소스**: pykrx 대신 **네이버 금융 편입종목 페이지**

  전혀 늘지 않는다(pykrx/pandas 불필요). 조회 시점 편입종목이 199개였음(정확히 200이
  아닐 수 있음 — 정상, 강제로 200 맞출 필요 없음).
- **시세/잔고/주문**: 한국투자증권 모의투자 API로 확정, 실제 토큰 발급·시세 조회까지
  라이브로 검증 완료(`.env`의 `KIS_APP_KEY`/`KIS_APP_SECRET`/`KIS_ACCOUNT_NO` 사용,
  모의투자 전용 도메인 `openapivts.koreainvestment.com:29443`만 호출). 토큰 발급은
  1분당 1회 제한이 있다. **코스피200 199종목 전체를 한투 API로 시세 조회하는 것도
  라이브로 검증 완료 — 199/199 전부 성공.** 단, 모의투자 계좌는 초당 요청 제한이
  꽤 빡빡해서(0.3초 간격도 부족, "초당 거래건수를 초과하였습니다" 에러) 요청 간
  최소 1초 간격 또는 유량 제한 감지·백오프 재시도가 필요하다 — 나중에 실제 KIS
  클라이언트를 만들 때 이 쓰로틀링을 반드시 반영해야 한다.
- **차트 데이터(OHLCV)는 계속 네이버 fchart 스크래핑** — 이미 구축된 `fetch_market_context`를
  코스피200 199종목 전수로 라이브 검증했고, 버그 하나를 발견해서 고쳤다: 거래정지
  종목(예: 한화/000880)은 네이버가 O/H/L/V를 전부 0으로 내려주는데(종가만 마지막
  값 유지), `compute_indicators`의 지지/저항 계산이 이 구간에서 0으로 나누기
  오류를 냈다. 무거래일(`volume == 0`)을 지지/저항 계산에서 제외하도록 수정
  (`collectors.py`). 수정 후 199/199 전부 정상 조회 확인.
