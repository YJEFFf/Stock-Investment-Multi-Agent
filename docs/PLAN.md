# 설계 배경과 근거

`CLAUDE.md`의 규칙들이 왜 그렇게 정해졌는지를 담은 문서.
규칙을 바꾸고 싶어질 때 여기를 먼저 읽을 것.

---

## 1. 이전 프로젝트의 실패

### 무엇이 있었나

한투 API + AWS EC2 + MySQL 기반 자동매매 시스템. 정량·기술적 지표로 후보를 거른 뒤
남은 종목의 데이터를 차트 이미지로 변환하고, Claude가 이미지를 분석해 신뢰도 점수를
매겨 문턱을 넘으면 매수하는 구조였다. 모의투자에서 약 10% 수익이 나왔다.

### 무엇이 문제였나

수익이 지속되지 않았고, **매수하면 안 되는 상황에서도 매수가 발생했다.**

구조적 원인은 스케줄러에 있었다. 15:35 장 마감 후부터 18~24시 매시 정각에,
pending 신호가 5개 미만이면 `pre_market_setup(is_retry=True)`를 재실행하는 로직이
있었다. 의도는 "분석이 덜 끝났으면 마저 하자"였지만, 실제 작동은 "5개를 채울 때까지
계속 돌린다"였다.

같은 후보를 반복해서 LLM에게 보여주면 언젠가는 통과한다. 문턱값을 낮춘 코드는 어디에도
없지만, **재시도 자체가 문턱을 낮추는 역할을 했다.**

### 왜 이게 치명적이었나

매일 매수가 강제되면 신호의 예측력을 측정할 수 없다. 어떤 매수가 "신호가 좋아서"이고
어떤 게 "할당량을 채워야 해서"인지 사후에 구분할 방법이 없기 때문이다.

그래서 "수익이 안 났다"와 "무리하게 샀다"는 별개 문제가 아니다.
**후자가 전자의 원인 진단을 불가능하게 만든 관계다.**

모의투자 10% 수익도 마찬가지로 해석 불가다. IC 같은 지표로 유의성을 확인하지 않았기
때문에, 몇 개 종목이 우연히 터진 결과일 가능성을 배제할 수 없다.

### 코드를 재사용하지 않는 이유

두 가지다. 하나는 위 결함이 스케줄링·재시도·상태 복원 로직 전반에 얽혀 있어서
부분 수정으로 걷어내기 어렵다는 것. 다른 하나는 그냥 다시 손대고 싶지 않다는 것이고,
이건 충분한 이유다. 사이드 프로젝트는 의욕이 연료다.

가져오는 것은 **워크플로우 지식**뿐이다. 휴장일 처리, 장 마감 후 분석 → 다음날 개장
매수 흐름, EC2 재기동 시 캐치업 같은 운영 노하우는 두 번째 구현에서 훨씬 빠르게 나온다.

## 2. 계층 설계의 근거

### 수집은 에이전트가 아니다

뉴스 크롤링, DART 조회, 시세 fetch는 전부 결정론적 ETL이다. 여기에 LLM을 붙이면
비용과 레이턴시만 늘고 재현성이 깨진다. LLM 호출은 판단이 필요한 지점에만 넣는다.

### 왜 강세/약세 토론 단계가 있나

LLM은 주어진 근거에 동조하는 편향이 강하다. 분석가들의 의견을 그대로 종합하면
긍정 방향으로 쏠린다. 반대 논거를 **명시적으로 생성하게 강제**해야 균형이 잡힌다.

### 에이전트 합의는 신뢰의 근거가 아니다

같은 base model 5개가 동의하는 것은 독립 표본 5개가 아니라 상관된 오류 1개다.
진짜 다양성은 모델이 아니라 **데이터 소스**에서 나온다. 차트만 보는 분석가와 공시만
보는 분석가가 다른 결론을 내는 건 의미가 있지만, 같은 뉴스를 두 번 읽히는 건 의미가 없다.

이것이 분석가를 데이터 소스 기준으로 나눈 이유다.

### 왜 리스크 게이트가 LLM이 아닌가

종목당 최대 비중, 섹터 집중도, 일일 최대 손실, 총 노출은 "판단"의 영역이 아니라
넘으면 무조건 거부하는 하드 룰이다. LLM에게는 거부권만 주고 승인권은 주지 않는다.

### 비용 구조

KOSPI200 전체에 분석가 4개를 돌리면 하루 800회 호출이다. 정량 필터로 후보를
10~20개로 줄인 뒤에 LLM을 투입하는 순서를 유지한다.

종목당 독립 호출(비교 금지) 원칙 때문에 호출 수가 늘지만, 무리한 매수를 막는 가장
효과적인 장치라 이 비용은 감수한다.

## 3. 측정에 대해

### 왜 백테스트 수익률을 믿으면 안 되나

정량 모델의 룩어헤드 편향은 코드로 막을 수 있다. 하지만 LLM은 2024년 뉴스를 읽으면
그 뒤에 주가가 어떻게 됐는지 이미 학습해서 알고 있고, 이건 모델 가중치 안에 있어서
막을 방법이 없다.

**LLM 컴포넌트가 들어간 시스템의 과거 구간 백테스트 수치는 참고용으로도 위험하다.**
워크포워드 또는 실시간 모의투자로만 검증한다.

### 왜 IC인가

IC(information coefficient)는 예측값과 실제 수익률의 순위상관이다.
0.03~0.05만 안정적으로 나와도 쓸 만한 신호다.

수익률부터 보면 몇 개 종목이 우연히 터진 것을 실력으로 착각하게 된다. IC를 먼저 보면
"신호가 전반적으로 방향을 맞히고 있는가"를 종목 수 전체에 걸쳐 확인할 수 있다.

## 4. 빅데이터 예측 모델에 대한 판단

### 왜 지금 넣지 않나

"데이터를 더 많이 넣으면 예측이 좋아진다"는 가정은 주식에서 잘 성립하지 않는다.
금융 시계열은 신호 대 잡음비가 극단적으로 낮아서, 데이터를 10배로 늘려도 모델이
학습하는 건 대부분 잡음이다. 시장 구조가 바뀌기 때문에 오래된 데이터는 오히려 해롭다.

규모 감각도 필요하다. KOSPI200 × 10년 일봉은 약 50만 행으로, 노트북 pandas에서 도는
크기지 빅데이터가 아니다. 진짜 빅데이터가 되려면 틱·호가창 레벨로 내려가야 하는데,
그 순간 인프라 비용이 급증하고 얻는 알파는 개인이 접근하기 어려운 초단타 영역이다.

그리고 더 근본적으로 — 이전 실패의 원인이 "예측력 부족"이 아니라 "문턱 부재"였다면,
아무리 좋은 모델을 넣어도 성능이 측정되지 않는다. 순서를 지켜야 한다.

### 넣게 된다면

가격 방향 이진 분류는 승률 52~53%가 현실적 천장이고 거래비용 빼면 남는 게 없다.
대신 이런 타깃이 낫다:

| 타깃 | 근거 |
|---|---|
| 횡단면 랭킹 (오늘 200종목 중 상대 순위) | 시장 방향을 맞힐 필요가 없어짐. 노이즈가 적음 |
| 변동성 예측 | 실제로 예측 가능성이 높은 몇 안 되는 영역. 포지션 사이징에 직접 쓰임 |
| 이벤트 후 이상수익률 | 공시 분석가와 직결. 라벨링이 명확하고 이벤트 스터디로 검증 가능 |

구조상으로는 별도 에이전트가 아니라 `agent="quant"` 분석가로 붙인다.
이때 `confidence`는 모델의 예측 확률이 아니라 **최근 60일 롤링 IC**로 잡는다.
모델은 틀리고 있을 때도 높은 확률을 뱉기 때문에, 최근 예측력이 무너지면 자동으로
발언권이 줄어들게 만들어야 한다.

| 룰 | 값 | rejected_by |
|---|---|---|
| 종목당 최대 비중 | 15% | `position_limit` |
| 섹터 집중도 한도 | 40% | `sector_concentration` |

마일스톤 1의 게이트 구현은 이 수치를 하드코딩된 상수가 아니라 설정값으로 분리해
나중에 백테스트/튜닝 시 코드 수정 없이 바꿀 수 있게 한다.

### 차트 분석가 입력 형태·시세 데이터 소스 (2026-08-08 확정)

- **입력 형태**: 이미지+vision이 아니라 텍스트(OHLCV + 파생 지표 수치)로 먼저
  시도한다. 차트 이미지를 보고 판단하는 것과 동등한 효과를 노리고 지표를
  추세(SMA)·모멘텀(RSI)·거래량·지지저항(최근 고가/저가)까지 커버하도록 구성.
  텍스트로 부족하다고 판단되면 그때 이미지+vision으로 전환한다 — 지금 미리
  만들지 않는다.
- **시세 데이터**: pykrx(무료, 인증 불필요) 대신 **네이버 금융 비공식 차트 API
  스크래핑**을 쓴다. pykrx의 실시간성이 부족하다고 판단해서 사용자가 직접 선택.
  비공식 엔드포인트라 구조가 바뀔 수 있음 — `collectors.py`의 수집 실패는 데이터
  수집 실패 경로로만 재시도한다 (규칙 4).

### 뉴스 분석가 데이터 소스 (2026-08-08 확정)

- **종목 뉴스**: `finance.naver.com/item/news_news.naver?code=<종목코드>` — 네이버가
  이미 종목코드로 정확히 매핑해주는 페이지라 우리 쪽에서 회사명 키워드 매칭을 할
  필요가 없다. **`Referer: finance.naver.com/item/news.naver?code=...` 헤더가
  없으면 빈 결과만 온다** — 이 헤더는 필수다.
- **업종(도메인) 뉴스**: 네이버에 종목처럼 깔끔한 업종별 뉴스 탭이 없다 (업종 상세
  페이지에도 없음, 자체 뉴스검색 기능은 테스트해보니 사실상 죽어 있음 — 항상 0건).
  대신 `finance.naver.com/news/` 전체 시황 허브를 긁어 헤드라인 중 업종명이 포함된
  것만 골라낸다. 회사명 매칭보다 오탐 허용 범위가 넓은 업종 단위라 키워드 매칭이
  실용적으로 괜찮다고 판단. 개별 기사 타임스탬프는 이 페이지에 없다.
- **뉴스 분석가 프롬프트 설계**: 종목 뉴스가 메인 판단 대상, 업종 뉴스는 "이 종목이
  속한 시장 배경" 참고용으로 명확히 구분해서 준다 — 종목 간 비교가 아니라 이 종목
  하나를 둘러싼 맥락이라 규칙 5(종목 비교 금지) 위반이 아니다.
- **개발 중 API 사용 원칙 (사용자 피드백, 2026-08-08)**: 개발·테스트 단계에서는
  Claude API를 실제로 호출하지 않는다 — 모든 자동 테스트는 모킹으로만 돈다. 실제
  API 확인은 `tests/test_live_smoke.py`에 최소 규모(종목 1개)로만 두고, 기본적으로
  스킵된다. 종목 여러 개 × 여러 날 규모의 실측정(`tests/test_live_signal_rate.py`
  같은)은 사용자가 명시적으로 요청하고 비용 규모를 먼저 확인했을 때만 실행한다.

### 공시 분석가 데이터 소스 (2026-08-08 확정)

- **DART(전자공시시스템) Open API**를 그대로 쓴다 — 차트·뉴스처럼 네이버를
  리버스엔지니어링할 필요 없이 금융감독원 공식 API가 있다. `DART_API_KEY`
  환경변수 필요(무료 발급, opendart.fss.or.kr).
- 두 엔드포인트 조합: (1) `corpCode.xml` — 전체 법인의 종목코드↔고유번호(corp_code)
  매핑을 ZIP으로 한 번에 받아 프로세스 생애주기 동안 메모리 캐시(자주 안 바뀌는
  데이터라 파일 캐시까지는 불필요), (2) `list.json` — corp_code로 종목별 공시 목록
  조회. **corp_code 없이 조회하면 전체 법인 대상 검색이 되어 종목당 독립 호출
  원칙(규칙 5)이 깨지므로 항상 corp_code를 채워서 요청한다.**
- `status="013"`(조회된 데이터 없음)은 에러가 아니라 정상적인 0건 상태로 처리 —
  뉴스 수집기의 "0건 vs 수집 실패" 구분과 동일한 패턴.
- **공시 원문(본문)은 가져오지 않는다** — 보고서명(`report_nm`) 자체가 한국 공시
  특성상 정보 밀도가 높아 뉴스 분석가와 같은 스코프(헤드라인/제목만)로 맞췄다.
  원문 크롤링은 나중에 필요성이 확인되면 추가.

### 마일스톤 3 착수 — IC 측정은 인프라만, 오늘 숫자는 안 나온다 (2026-08-08)

차트·뉴스·공시 세 분석가가 다 붙어서 §3(측정) 단계로 넘어갔다. 여기서 중요한 제약을
다시 확인함: **오늘 당장 IC를 계산할 수 없다.** IC는 (그날 예측 점수, 그 이후 실현
수익률)의 순위상관인데, 뉴스·공시 수집기는 "오늘 시점" 데이터만 긁어오지 과거 특정
날짜의 스냅샷을 재구성하지 못한다 — 그리고 설사 됐다 해도 §3이 이미 명시한 대로
LLM 컴포넌트에는 백테스트 대신 워크포워드·실시간 모의투자만 쓰라고 못 박혀 있다.

그래서 이번에 만든 건 **인프라**뿐이다 (`src/evaluation.py`):
- `information_coefficient(pairs)` — 스피어만 순위상관, 순수 파이썬(외부 의존성 없음).
- `compute_forward_return(ticker, as_of, forward_days)` — 차트 수집기(무료)로 실현
  수익률 계산. `as_of` 이후 데이터가 아직 없으면 None — 이게 "시간이 지나야 한다"는
  제약이 코드로 드러나는 지점이다.
- `summarize_ic(log_path, forward_days)` — 로그에 쌓인 예측과 실현 수익률로 일별
  횡단면 IC의 평균·표준편차 계산.

실제로 IC 숫자를 얻으려면: 앞으로 매일 파이프라인을 실제로 돌려 `logs/pipeline.jsonl`
(임시 tmp_path 말고 진짜 경로)에 예측을 쌓고, 며칠~몇 주 뒤 `summarize_ic`를 돌린다.
`run_day`가 남기는 로그에는 이제 `avg_score`/`avg_confidence`가 필드로 들어간다
(전에는 `Decision.reason` 문자열 안에만 있었음).

### 판단 계층 구현 — 강세/약세 토론 + 포트폴리오 매니저 (2026-08-08 확정)

`pipeline.propose_decision()`(평균 점수 ≥0.85 문턱)이 임시로 대신하던 "판단: LLM"
계층을 실제로 구현했다 (`src/judgment.py`). 구조: 종목 하나의 분석가 의견을 받아
강세 논거·약세 논거를 **서로의 출력을 못 보게 독립적으로** 생성(`asyncio.gather`)한
뒤, 포트폴리오 매니저가 분석가 의견+양쪽 논거를 종합해 BUY/HOLD를 최종 판단한다.

- **왜 두 방향을 강제로 생성하는가** (docs/PLAN.md §2): LLM은 주어진 근거에 동조하는
  편향이 있다. 강세/약세를 데이터가 한쪽으로 쏠려 있어도 억지로 둘 다 만들게 해서
  균형을 잡는다.
- **규칙 6과의 관계**: 매니저가 BUY를 직접 말해도 규칙 위반이 아니다 — 그건 추천일
  뿐, 그 뒤 리스크 게이트(코드)가 최종 승인권을 갖는다. 매니저의 HOLD는 그대로
  확정(매수 없음)되고 매니저의 BUY는 게이트가 거부할 수 있다는 게 "LLM은 거부권만
  가진다"의 실질적 구현이다.
- **`AnalystOpinion`은 안 건드렸다.** CLAUDE.md가 준 고정 계약(score/confidence/
  evidence만, reasoning 텍스트 없음)이라 토론 단계는 각 분석가의 숫자 패턴만 보고
  논거를 만든다 — 원문 reasoning까지 주려면 계약을 바꿔야 해서 안 했다. 대신 새로
  만든 `DebateArgument`(자유 설계 가능한 신규 타입)와 `Decision.debate`/
  `Decision.evidence`(감사 추적용, 기본값 있는 optional 필드)는 추가했다.
- `pipeline.run_day()`가 `judge_fn` 파라미터를 요구하도록 바뀌었다 — 기본값 없음,
  호출부가 항상 명시적으로 골라야 한다. 비용 없는 더미/측정용은
  `pipeline.propose_decision`(그대로 유지, 삭제 안 함), 실제 판단은
  `judgment.judge`.

### 정량 사전 필터 (2026-08-08)

코스피200 전체에 분석가를 돌리면 하루 800회 호출이라(§2) `pipeline.quant_prefilter`를
LLM 분석가 앞단에 뒀다. **품질 필터가 아니라 비용 게이트**다 — "이 종목이 좋다"가
아니라 "오늘 이 종목에 평소보다 뭔가 있다"만 판정하고, 방향 판단은 전적으로 LLM
분석가 몫으로 남긴다.

세 조건을 OR로 절대 문턱 판정(`pipeline.passes_quant_filter`):
- 거래량이 20일 평균 대비 2배 이상
- RSI14가 70 이상(과매수) 또는 30 이하(과매도)
- 코스피200 지수 대비 5일 초과수익률 절대값 5% 이상

top-N이 아니라 절대 문턱이라 통과 개수는 매일 다르고 0일 수도 있다(규칙 2·3).
세 값 다 관행값(RSI 30/70은 Wilder 원안, 나머지는 흔한 스크리너 휴리스틱)으로
시작했고, 이 프로젝트 데이터로 튜닝한 값이 아니다 — 나중에 필터 통과율 로그가
쌓이면 그 분포(과하게 관대한지/인색한지)를 보고 조정하되, 과거 수익률에 맞춰
역산하지 않는다(그건 §3이 경고하는 backtest 함정과 같은 종류의 문제).

**레짐 강건성**: 수익률 조건을 종목 절대 수익률이 아니라 지수 대비 초과수익률로
잡았다 — 시장 전체가 같이 움직이는 날(폭락/급등)에 대부분 종목이 동시에 걸려서
정확히 비용이 가장 크게 튀는 날 후보가 쏠리는 걸 막기 위해서다. 거래량·RSI
조건은 여전히 개별 종목 절대값이라 이 한계가 남아있다 — 의도적으로 남겨둔
디자인이다: "레짐 분류기"를 따로 만들어 문턱을 자동 조정하는 방식은 나중에
"레짐이 안 좋으니 문턱을 조정하자"는 식으로 규칙 2·3을 우회하는 통로가 될 위험이
있어서, 대신 실제로 후보가 몰리면 로그에 그대로 남기고 사용자가 보고 판단하게
둔다 — 자동으로 걸러내지 않고 투명하게 노출.

### 정량 필터 실측 결과 및 수정 — 초과수익률 정규화 (2026-08-08)

구현 직후 코스피200 199종목 전체로 실측했더니 **188/199(94.5%)가 통과했다** —
비용 게이트로서 사실상 기능을 못 하는 수준. 원인을 종목별로 분해해보니
`excess_return` 조건 하나가 거의 전부를 만들고 있었다(150종목은 이 조건
하나로만 통과, 거래량·RSI는 추가로 걸러낸 게 0건). 그날 코스피200 지수가
5일간 -6.9% 빠졌던 게 원인 — **지수가 크게 움직인 주엔 종목 간 수익률 분산
자체가 커져서, 지수 대비 고정 5%p 문턱으로는 대부분의 종목이 걸린다.** 절대
수익률 문턱이 가진 레짐 취약성을 지수 대비로 옮겼을 뿐 근본 문제(고정폭이
변동성 변화에 안 맞음)는 그대로 남아있었던 것.

이 하루치 숫자에 맞춰 문턱값을 손으로 조정하는 건 하지 않았다 — 오늘 딱 맞는
값을 찾아도 다음에 조용한 주가 오면 또 안 맞고, 이건 top-N을 다른 자리에서
재현하는 것과 같은 함정이다. 대신 구조를 고쳤다: `collectors.compute_indicators`에
`daily_return_stdev_20d`(종목 자신의 최근 20일 일별 수익률 표준편차)를 추가하고,
초과수익률을 고정 %p가 아니라 **이 값을 5일치로 스케일(×√5)한 "기대 변동폭"
대비 몇 배인가(z-score)**로 판정하도록 바꿨다(`QUANT_EXCESS_RETURN_Z_THRESHOLD = 2.0`).

시장이 흔들리는 주엔 종목 자신의 변동성도 같이 커지므로 문턱이 자동으로
따라 올라간다 — 매일 일정 비율이 통과하도록 구조적으로 보장하는 횡단면
z-score(반려한 방식, 규칙 2·3 우회 소지)와 달리 종목 자신의 시계열 대비라
그런 보장이 없다.

수정 후 같은 199종목으로 재검증: 94.5% -> 41.2%로 절반 넘게 줄었다. 다만
41.2%도 여전히 높다 — 자기 변동성 정규화는 후행 지표(최근 20일 평균)라
레짐이 막 바뀌는 시점엔 "정상 변동폭" 기준 자체가 아직 낮아서 일시적으로
과민하게 반응하는 게 정상이다. 이 숫자 하나에 맞춰 문턱을 더 조이지 않았다 —
그러면 오늘 하루에 과적합하는 것과 같은 함정이다. 여러 날(특히 조용한 날
포함) 로그가 쌓인 뒤 분포를 보고 판단한다.

### 매도 로직 1단계 — 결정론적 안전장치 (2026-08-09 확정)

CLAUDE.md가 "아직 정해지지 않은 것"으로 남겨뒀던 매도 로직에 착수했다. 매수와
근본적으로 다른 지점이 있다는 게 설계의 핵심 전제: 매수는 판단을 미루면 현금
(안전)이지만, 매도는 판단을 미루면 손실 종목을 계속 들고 있는 것이라 "판단
안 함 = 안전"이 성립하지 않는다. 그래서 순수 LLM 재량 대신 **결정론적 안전장치
+ LLM 재량 하이브리드**로 가기로 했고, 이번엔 안전장치만 구현했다(`src/sell.py`,
`pipeline.py`와 분리 — 고치는 이유가 다름).

**확정 수치**:
- 손절선: 진입가 대비 -10% (`STOP_LOSS_PCT`) — 전량 매도.
- 익절: 진입가 대비 +20%에서 첫 트리거, 전량이 아니라 **현재 보유량의 1/3만
  매도**하고 계속 들고 간다 — 상승 여지를 남겨두기 위해서다.
- 이후엔 진입가가 아니라 **고점 대비 트레일링 스톱**으로 전환: 고점에서 일정
  비율(`TAKE_PROFIT_TRAIL_PCT`, 제안값 -7% — 사용자가 정확한 수치를 아직
  확정 안 함, 관행값으로 시작 후 로그 보고 조정) 조정되면 다시 1/3 매도.
  트리거가 발동할 때마다 고점을 그 시점 가격으로 리셋한다 — 안 그러면 같은
  하락 하나로 여러 단계가 연달아 발동해버린다.
- 이 사이클은 상한 없이 반복된다 — 강제로 3번에서 끊지 않는다. `(2/3)^n`이라
  전량 청산되는 일 없이 항상 일부가 남아 계속 상승 여지를 갖는다(사용자
  의도 그대로).

**규칙 6과의 관계**: 리스크 게이트는 "새 매수를 막는" 장치다. 결정론적 매도는
게이트를 거치지 않는다 — 보유분을 줄이는 행위 자체가 위험을 낮추는 방향이라
"한도 초과" 개념이 성립하지 않는다.

**스키마**: `Position`에 `entry_price`/`peak_price`/`take_profit_stage` 추가.
`entry_price`가 `None`인 포지션은 매도 평가 자체를 건너뛴다 — `AnalystOpinion`이
"판단 불가"와 "판단했으나 기각"을 구분하는 것과 같은 패턴. 매도는 `Decision`과
완전히 분리된 `SellAction` 타입으로 만든다 — `Decision.action` 주석이 애초에
"매도는 별도 경로"라고 못 박아뒀다.

**알려진 갭 — 매수 실행 경로가 아직 진입가를 안 채운다**: `pipeline.execute()`
(신규 매수 실행)는 지금 가격 정보를 전혀 다루지 않아서(`weight`만 씀),
`Position.entry_price`가 실제로 채워지지 않는다. 매도 로직이 실제로 작동하려면
매수 시점에 현재가를 어디서 가져와 `entry_price`/`peak_price`를 초기화할지
먼저 결정해야 한다(예: 판단에 쓰인 `MarketContext`의 최신 종가를 `Decision`까지
끌고 올지, 아니면 집행 시점에 KIS로 별도 시세를 다시 조회할지). 다음 단계로
남겨뒀다.

**아직 구현 안 함**: LLM 재량 매도(분석가가 보유 종목을 재평가해 "확신이
무너졌다"고 판단하면 매도를 제안하는 경로) — 결정론적 안전장치가 먼저 자리잡은
뒤에 얹기로 했다.

### 진입가 배선 — 실제 KIS 모의투자 주문 집행 (2026-08-09 확정)

위에서 남겨뒀던 갭(매수 실행 경로가 진입가를 안 채움)을 실제로 풀었다. 판단은
전일 데이터로 미리 해두더라도, 집행은 시장가 주문 + 갭 체크로 하기로 했다 —
사용자 확정: "전날 종가 기준으로 다음날 매수를 걸어놓으면 안 사질 때도 있다"는
게 이유. 장 시작가가 전일 종가 대비 ±3%(사용자 확정치) 넘게 벌어지면 판단
근거가 낡았다고 보고 매수를 스킵한다 — 강행하지 않는다는 점에서 규칙 2·3과
같은 정신.

**`src/kis.py`에 추가된 것**: `fetch_current_price`(실시간 현재가),
`fetch_account_balance`(계좌 총평가금액 — `PortfolioState`는 비중만 들고 절대
금액을 안 쌓아서, 비중을 실제 주수로 환산하려면 매번 브로커를 잔고의 출처로
삼는다), `place_market_buy_order`(시장가 매수 주문 접수, 주문번호 반환),
`fetch_fill_price`(그날 그 종목의 평균 체결가 — 주문별 체결 내역이 아니라
집계 필드 `pchs_avg_pric`를 쓴다). GET 전용이던 `_kis_get`을 `_kis_request`로
리팩터링해 POST(`_kis_post`, 주문 접수용)까지 공통 재시도·쓰로틀링 로직을
공유하게 했다.

**라이브로 실측 검증한 것(2026-08-09)**: 계좌번호 상품코드가 "01"임을 확인
(잔고조회 정상 응답), 잔고조회 API가 사용자가 설정한 초기자금 1억원과 정확히
일치하는 `tot_evlu_amt`를 반환함을 확인, 현재가 조회 정상 확인. **주문 접수는
구조만 확인됐다** — 파라미터·계좌 인증은 정상 처리됐지만 응답이 "모의투자
영업일이 아닙니다"(그 시점 장이 닫혀 있었음)라 실제 체결까지는 못 봤다.
체결가 조회의 `output1`(주문별 상세) 필드명은 실제 체결 건이 없어 확인 못
했고, 대신 필드명이 이미 확인된 `output2`(집계) 쪽으로 우회했다. **장중에
실제 매수가 한 번 나가면 이 부분을 재검증해야 한다.**

**`pipeline.execute_buy_order`(신규, 비동기)**: 기존 `execute()`(순수 함수,
가격 개념 없는 시뮬레이션 전용, 무비용 테스트 경로로 계속 남김)와 분리했다.
갭 체크 → 잔고 조회 → 수량 계산(`floor(총평가금액 x weight / 현재가)`) → 주문
접수 → 체결가 조회 → `Position.entry_price`/`peak_price` 설정 순서. 가격·잔고
조회 실패나 주문 거부 등 어느 단계에서든 실패하면 매수 없이 그대로 반환한다
(규칙 1: 기본 상태는 현금). 기존 포지션에 추가매수하는 경우는 비중 가중평균으로
진입가를 갱신하는데, `weight`가 "그 시점 총자산 대비 비중"이라 총자산이 매수마다
달라지면 완전히 정확하진 않은 근사치다 — 추가매수는 드문 경로라 이 정도면
충분하다고 판단.

### 매도 로직 일별 배선 — evaluate_holdings (2026-08-09)

`src/sell.py`의 손절/트레일링 익절 평가 함수들이 그동안 파이프라인 어디에서도
호출되지 않고 있었다 — `pipeline.evaluate_holdings()`로 매일 실행되게 연결했다.

매수 쪽엔 정량 필터가 있지만 이쪽엔 없다. 필요가 없기 때문이다: 리스크
게이트가 종목당 최대 비중을 15%로 막아둬서 보유 종목 수 자체가 원천적으로
적다(최대 ~7개). 그래서 비용 게이트 없이 보유 종목 전부를 매일 그냥 평가한다.

흐름: 보유 종목 전체의 현재가를 KIS로 동시 조회(`asyncio.gather`) → 고점
갱신(`sell.update_peak_price`) → 손절/익절 평가(`sell.evaluate_deterministic_sell`)
→ 트리거되면 집행(`sell.execute_sell`) → `logs/sell.jsonl`에 기록. 가격 조회가
실패한 종목은 그날 평가를 건너뛴다 — collectors/kis 단에서 이미 재시도를
소진한 뒤라 여기서 다시 재시도하지 않는다(규칙 4). 한 종목의 실패가 다른
보유 종목 평가를 막지 않는다.

LLM 재량 매도는 여전히 미구현 — 결정론적 안전장치만 이 함수로 매일 돈다.

### LLM 재량 매도 + 실주문 배선 완성 (2026-08-09)

남아있던 두 갭(LLM 재량 매도 미구현, 실제 주문 집행이 판단 체인에 안 이어짐)을
마저 이어붙였다.

**LLM 재량 매도**: 매수 쪽 강세/약세 토론 + 포트폴리오 매니저와 대칭 구조로
만들었다(`judgment.debate_holding`, `judgment.portfolio_manager_sell`,
`judgment.judge_sell`). 매수용 프롬프트를 재사용하지 않고
`prompts/debate_stay.md`/`debate_exit.md`/`portfolio_manager_sell.md`를 새로
썼다 — "매수할까"와 "계속 들고 있을까"는 다른 질문이라 매수용 프레이밍을
그대로 쓰면 LLM이 엉뚱한 질문에 답하게 된다. `DebateArgument.stance`는
bull=존버/bear=이탈로 그대로 재사용(신규 stance 불필요).

규칙 6과 다르게 설계한 지점: 매수용 포트폴리오 매니저는 게이트가 뒤에서
거부할 수 있다는 전제로 "적당히 관대해도 된다"고 프롬프트에 명시하는데,
매도용 매니저는 정반대로 "네 SELL은 그대로 실행된다, 그러니 확신 없으면
HOLD가 기본"이라고 프롬프트에 명시했다 — 게이트가 없는 대신 프롬프트 자체의
보수성으로 상쇄한다.

`pipeline.evaluate_holdings`에 `analyst_fn`/`judge_sell_fn`을 옵션으로
추가했다(기본값 `None` — 안 넣으면 이 계층 자체가 꺼진다). 결정론적 매도가
이미 트리거된 종목은 LLM에게 다시 묻지 않는다(코드가 이미 팔기로 정한 걸
재확인할 이유가 없다). analyst_fn/judge_sell_fn을 옵션(None 기본)으로 둔 건
`execute_fn`류(기본값 없음, 항상 명시)와 의도적으로 다른 결정이다 —
결정론적 안전장치는 항상 켜져 있어야 하지만, LLM 재량은 진짜 선택적 추가
비용이라 안 켜는 쪽이 안전한 기본값이다.

**실주문 배선**: `run_day`/`run_daily`가 `execute_fn`을 필수 인자로 받도록
바꿔서 `execute_buy_order`(실제 KIS 주문)를 실제로 꽂을 수 있게 했다 —
이전엔 이 함수가 있어도 아무도 안 불렀다. 무비용 시뮬레이션 경로는
`execute_simulated`(`execute()`의 비동기 래퍼)로 남겨 기존 테스트가 그대로
돌게 했다. 매도도 대칭으로 `SellExecuteFn`(`execute_sell_simulated` vs
`execute_sell_order`)을 만들어 `evaluate_holdings`에 필수 인자로 추가했다.

**실제 매도 주문을 위해 필요했던 것**: `Position`에 `quantity`(실제 보유
주수)를 추가했다. `weight`는 비중일 뿐이라 매도 시 몇 주를 팔지 알 수
없었다 — `execute_buy_order`가 실제로 주문을 넣은 수량을 그대로 저장해두는
쪽을 택했다(브로커를 다시 조회하는 대신 — 이미 우리가 아는 값이라 조회할
필요가 없고, 미검증 필드명에 의존하는 리스크도 없다). `quantity`가 없는
포지션(순수 시뮬레이션 `execute()`로 연 포지션)은 실제로 판 적이 없으니
`execute_sell_order`가 실주문 없이 상태만 시뮬레이션으로 갱신한다.

`kis.py`에 `place_market_sell_order` 추가 — `place_market_buy_order`와 완전히
대칭(같은 엔드포인트, tr_id만 다름). 매수와 마찬가지로 라이브로 구조 검증만
했다("모의투자 영업일이 아닙니다" 응답 — 계좌·파라미터는 정상 처리 확인,
실제 체결은 장중 재검증 필요).

### 정량 필터 상한 재검토 — 상한 없음으로 확정 (2026-08-09)

AWS에 올려 스케줄러로 매일 자동 실행하기로 하면서, 사용자가 "정량 필터 통과
종목을 15개로 상한을 걸어야 하는 것 아니냐"고 확인을 요청했다. 확인 결과:
**`quant_prefilter`엔 상한이 코드로도, 설계상으로도 없다.** 세션 초반에 내가
"~15개 정도 나올 것 같다"고 말한 적은 있지만 그건 예상치였을 뿐, 실제 구현
시점엔 규칙 2(목표 신호 개수 금지, top-N 선택 금지)에 따라 절대 문턱만 쓰고
개수 상한을 의도적으로 넣지 않았다 — 상한을 걸려면 통과 종목 중 "상위 N개"를
추릴 기준이 필요한데, 그건 이전 프로젝트를 무너뜨린 패턴(문턱을 우회해 억지로
채우기)과 방향만 반대일 뿐 같은 종류의 문제(정해진 개수를 맞추려고 뭔가를
선택)다.

토큰 비용 우려가 실제로 근거가 있는지 계산해봤다: 종목 1개가 필터를 통과해
끝까지 가면 LLM 호출 6회(분석가 3 + 토론 2 + 매니저 1), 종목당 약 $0.015
(Sonnet 5 인트로가 기준). **200종목이 전부 통과하는 최악의 경우에도 하루
$3~4.5 수준**(정가 기준으로도 $4.5) — 우려했던 것만큼 크지 않다는 게 확인됐다.
이 숫자를 보고 사용자가 상한 없이 그대로 가서 실측 데이터로 나중에 보정하는
쪽으로 확정했다. 코드 변경 없음 — 원래 설계 그대로 유지.

### 실전 검증 계획 (2026-08-09 확정)

- **월요일(장 개장)**: 종목 1개로 실제 매수 주문 → 체결가 조회 →
  `entry_price` 반영 확인, 그 자리에서 바로 매도 주문(`execute_sell_order`)까지
  왕복 검증. LLM 호출 없이 순수 KIS API 확인이라 비용 거의 없음.
- **화요일부터**: 월요일 검증에 문제 없으면 매일 전체 파이프라인을 실제로
  돌리기 시작한다 — `run_daily`(매수 판단, `logs/pipeline.jsonl`)와
  `evaluate_holdings`(매도 평가, `logs/sell.jsonl`) 둘 다 모든 부분에서 로그를
  남긴다. 정량 필터 통과 종목 수 상한 없음(위 결정 참고).
- **AWS 배포**: 서버에 올려 스케줄러로 매일 자동 실행할 계획 — 아직 착수 전,
  별도 작업으로 남아있다(컨테이너화, 시크릿 관리, 스케줄러 선택 등 미정).

### 휴장일 판정 + cron 실패 알림 (2026-08-09)

AWS 배포 직후 남겨뒀던 두 갭(휴장일에도 cron이 그대로 돌아 비용 낭비, cron 실패가
SSH 없이는 안 보임)을 마저 메웠다.

**휴장일 판정 (`src/market_calendar.py`)**: KRX 실시간 시세로 "오늘 거래일인지"를
역산하는 방법도 검토했지만 버렸다 — cron이 09:10 KST에 도는데 그 시각에 당일 일봉이
이미 채워져 있는지 타이밍이 불확실해서 판정 자체가 불안정해진다. 대신 KRX가 연초에
미리 공표하는 2026년 휴장일 15개를 정적으로 박아뒀다(`is_krx_trading_day`, 요일
계산으로 대체공휴일 적용 여부까지 교차검증). 연도가 안 맞으면(예: 2027년 진입 후
갱신 전) 조용히 잘못된 판단을 내리는 대신 `ValueError`를 던지도록 했다 — 이건 규칙
4가 금지하는 "결과가 마음에 안 들어서 재시도"와는 다른 종류의 유지보수(알려진
스케줄을 옮겨적는 작업)라 매년 갱신이 필요해도 우회로 보지 않는다.
`scripts/run_daily.py`의 `main()` 맨 앞에서 KST 기준 오늘 날짜로 체크해서, 거래일이
아니면 어떤 LLM/KIS 호출도 없이 즉시 반환한다.

**cron 실패 알림 (`src/notify.py`)**: 텔레그램 봇으로 발송(사용자가 이메일/Slack/
Discord/SNS 중 텔레그램을 선택). 알림 전송 자체가 실패해도 예외를 삼킨다 — 알림
실패 때문에 원래 실패의 로그(`logs/cron.log`)가 안 남으면 SSH로도 원인 파악할

실패 시(매수 판단은 계속 진행하는 기존 흐름은 유지, 알림만 추가), (2) `main()`
전체가 예외로 죽을 때(알림 보낸 뒤 그대로 재raise해서 cron의 실패 종료 코드는
유지). 토큰/chat_id는 사용자가 직접 `.env`에 채워 넣는 방식으로 전달받았다 — 채팅
전달은 시크릿이 대화 기록에 영구히 남는 문제가 있어 배제(과거 AWS 루트 키 노출
사고와 같은 이유). 로컬 `.env`를 EC2 `~/sima/.env`로 그대로 동기화해서 반영.

### 실거래 데이터로 학습하는 quant 분석가 — 방향만 합의, 구현은 보류 (2026-08-09)

자동매매가 돌기 시작하면서 사용자가 "이 프로젝트 자체가 쌓는 실거래 데이터(진입
시점 지표 → 실제 이후 수익률)로 학습해서 판단에 참고하면 어떻겠냐"고 제안했다.
이전 프로젝트를 무너뜨린 버그(재시도가 사실상 매수 할당량으로 작동)와는 인과관계가
반대라는 점은 맞다 — 다만 **어떻게 반영하는지**에 따라 안전/위험이 갈린다는 점을
짚고 넘어갔다.

- **안전한 형태**: 축적된 실거래 결과로 별도의 `quant` 분석가(통계/ML 모델)를
  학습시켜 다른 분석가와 동일하게 종목당 독립 호출로 `AnalystOpinion` 하나만
  내놓게 하는 것. 규칙 5(종목 간 비교 금지)·6(LLM은 거부권만)과 충돌하지 않는다 —
  "정량 ML 분석가" 항목으로 이미 열어둔 결정과 같은 방향(§"아직 정해지지 않은 것").
- **위험한 형태**: "전에 이런 상황에서 사서 이렇게 됐다"는 서술을 LLM 프롬프트에
  직접 끼워 넣는 것. 시간축으로 종목 비교를 우회하는 셈이고, 최근 성과에 판단이
  정서적으로 결합될 위험이 있다(문턱을 낮추는 대신 판단을 위축시키는 방향이라도
  "그날의 증거가 아닌 다른 것에 판단이 좌우된다"는 점에서 같은 종류의 문제).

없다 — 정량 필터 초과수익률 임계값을 튜닝할 때 이미 겪은 "관측치 하나로 과적합"
함정과 같은 리스크다.

**결정**: 방향(안전한 형태 = 별도 `quant` 분석가로만 반영)에는 합의했지만, 구현은
실거래 데이터가 유의미하게 쌓인 뒤로 미룬다. 지금 코드 변경 없음.

### 감시 지표 자동 집계 (2026-08-09)

CLAUDE.md "감시 지표" 섹션이 요구하는 3가지(최근 20영업일 매수신호 비율, 게이트
거부사유별 건수, 분석가별 호출수·실패율·토큰사용량) 중 앞 둘은 `pipeline.summarize_log`
함수로 이미 계산 가능했지만 **아무 데서도 호출되지 않고 있었고**, 뒤 하나는 집계
코드 자체가 없었다(`llm.py`가 호출마다 토큰은 로그로 남기지만 어떤 분석가 호출인지
식별할 라벨이 없어 사후에 분석가별로 못 나눴다).

**`llm.call_structured`에 `label` 파라미터 추가**: 이 함수는 차트/뉴스/공시
분석가와 토론(bull/bear/stay/exit)·매니저(매수/매도)가 전부 공유하는 단일 통로라,
여기서 라벨을 안 남기면 사후에 호출을 분석가별로 귀속시킬 방법이 없다. 매 호출의
최종 결과(성공/실패, 시도 횟수, 누적 input/output 토큰)를 `logs/llm_calls.jsonl`에
한 줄씩 남긴다 — `pipeline.py`의 `_append_log`와 같은 JSONL 적재 패턴을 그대로
따랐다(모듈이 달라 순환 임포트를 피하려 `llm.py`에 작게 중복 구현).

**`pipeline.summarize_recent_trading_days`**: 기존 `summarize_log(total_days)`는
로그 파일 전체를 total_days로 나누는 구조라 "정확히 N일치만 담긴 로그"를
전제한다(마일스톤1 시뮬레이션 테스트가 그렇게 씀) — cron이 매일 같은 파일에 계속
이어 쓰는 실환경에서는 이 가정이 깨진다. 로그에 남은 서로 다른 날짜 중 최근
n_days개만 추려서 그 위에서 집계하는 래퍼를 새로 추가했다(기존 `summarize_log`는
테스트 호환을 위해 그대로 둠).

**`pipeline.summarize_llm_calls`**: `logs/llm_calls.jsonl`을 label별로 묶어
호출수·실패율·토큰합계를 낸다. `since` 파라미터로 최근 창(달력일 30일 ≈ 영업일
20일 — 리포트 조회창일 뿐이라 정밀할 필요 없음)만 볼 수 있다.

**`scripts/run_daily.py`가 매일 실행 끝에 두 집계를 로그로 남긴다**
(`_log_monitoring_summary`, `monitoring_signal_rate`/`monitoring_llm_calls` 로그
라인 — `logs/cron.log`로 그대로 흘러간다). **의도적으로 읽기 전용이다**: 이 집계
결과를 판단 로직 어디에도 입력으로 되먹이지 않는다 — 방금 위 항목에서 짚은 "과거
데이터가 판단에 개입하면 위험하다"는 원칙을 모니터링 자체에도 그대로 적용한 것.

### 매매일지용 체결 기록 — `logs/trade_journal.jsonl` (2026-08-09)

사용자가 "로그를 최대한 많이 남기고 싶다"고 요청하면서, 나중에 노션과 연결해
매매일지(포트폴리오 서사)를 쓸 때 필요한 데이터가 지금 안 남고 있는지 점검했다.
사람이 나중에 수동으로 채울 여지(메모·태그 등)는 없고 **전부 자동 기록만** —
사용자가 명시적으로 확인.

점검 결과 실제로 큰 구멍이 있었다: `pipeline.jsonl`/`sell.jsonl`은 "판단이
게이트를 통과했는지"까지만 기록하고, **실제 체결 사실(체결가·수량·주문번호)과
그 판단을 만든 근거(분석가 의견·토론 논거·매니저 사유)는 어디에도 구조화된
형태로 안 남고 있었다.** 갭 초과/잔고 조회 실패로 매수가 스킵돼도
`pipeline.jsonl`엔 `approved: true`로만 남아 실제로는 안 산 걸 산 것처럼 보이는
상태였다. 실현손익(realized P&L)을 계산하는 코드도 전혀 없었다.

**대응**: 판단 로그(`pipeline.jsonl`/`sell.jsonl`, "게이트가 뭘 걸렀나" 관점)는
그대로 두고, 별도로 `logs/trade_journal.jsonl`을 추가해서 **실제 체결이 일어나는
지점**(`execute_buy_order`/`evaluate_holdings`)에서 한 이벤트당 한 줄씩 남긴다.

- **매수 이벤트**: 체결가·수량·KIS 주문번호·갭 비율 + `decision.model_dump()`
  전체(분석가별 점수·evidence, 강세/약세 토론 논거, 매니저 최종 사유) — 개별
  필드를 손으로 골라서 남기지 않고 `Decision` 객체를 통째로 직렬화했다. 나중에
  `Decision`에 필드가 늘어도 로그가 자동으로 따라가고, 지금 당장 어떤 필드가
  "매매일지에 중요한지" 미리 고르지 않아도 된다.
- **매도 이벤트**: 매도 사유(`stop_loss`/`take_profit_trail`/`llm_discretionary`),
  LLM 재량 매도일 때의 실제 판단 사유 텍스트(`SellAction.reasoning` — 이전엔
  `portfolio_manager_sell`이 생성만 하고 버렸다), 체결가, 진입가 대비
  실현손익률, 보유일수.

**스키마 변경 (최소, 기존 계약 안 건드림)**: `Position.entry_day: date | None`
(최초 진입일 — 추가매수해도 갱신 안 함, 보유기간 계산용), `SellAction.reasoning:
str | None`(결정론적 매도는 룰이 근거 그 자체라 None으로 남는다). 둘 다 optional
필드 추가라 `Decision.debate`/`Decision.evidence`를 추가했을 때와 같은 패턴.

**보유기간·실현손익 계산 위치**: `evaluate_holdings`가 실제 매도를 실행하기
직전의 `position`(entry_price/entry_day 보존된 상태)과 `current_price`를 그대로
갖고 있어 여기서 계산한다 — `sell.execute_sell_order`는 체결가를 별도로 다시
조회하지 않고(매수 쪽 `fetch_fill_price`와 비대칭 — 아직 안 맞춤, 장중 재검증
과제 중 하나) `current_price`를 그대로 체결가로 쓰기 때문에 이 지점의 값이
정확하다.
