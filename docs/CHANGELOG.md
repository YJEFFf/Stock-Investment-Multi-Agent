## 2026-09-01 (3차 — 게이트 누적 우회 수정. 발견 1을 닫는다)

앞 항목에서 "안 고친 것"으로 남겨뒀던 발견 1을, 상세 설명 후 사용자가 고치기로 확정.

### 원인 — `execute_fn`이 게이트의 누적을 끊고 있었다

`run_day`는 승인분이 반영된 포트폴리오를 다음 종목 게이트에 넘기는 구조다:

```python
gate_result = check_gate(decision, portfolio, config, TRADE_WEIGHT)
portfolio = await execute_fn(decision, gate_result, portfolio, sector, TRADE_WEIGHT)
#  ^^^^^^^ 이 한 줄이 total_exposure의 누적 판정을 가능하게 한다
```

그런데 운영 경로(`decide_buys._make_recording_execute_fn`)는 승인만 기록하고
**받은 포트폴리오를 그대로 돌려줬다.** "실제로 사지 않는다"는 의도는 맞았지만
부작용으로 누적도 같이 끊겼고, 그날 후보 **전부가 08:30 스냅샷 하나**를 상대로
독립 판정됐다. N건이 각자 한도 안이라는 이유로 다 통과하고, 합쳐서 넘는 건 아무도
안 봤다.

### 수정 — 승인분을 메모리 안에서만 얹는다

```python
return pipeline.execute(decision, gate_result, portfolio, sector, trade_weight)
```

`execute()`이지 `execute_buy_order()`가 아니다 — 가격 개념이 없는 순수 시뮬레이션이라
KIS를 안 부른다(규칙 7). 여기서 생기는 포지션은 게이트 산수를 위한 가상의 것이고,
이 스크립트는 상태 파일을 **읽기만** 하므로 디스크에 안 남는다. 실제 주문과 실제
진입가는 09:01 `execute_open`이 낸다.

### 실측 — 9/1 마감 상태로 재현

현금 50,308,183원 / 보유 7종목에서 같은 섹터 후보 8개가 전부 매니저 BUY를 받았다고 두면:

```
수정 전: 게이트 승인 8건                                  -> 주문 총액이 예수금 초과
수정 후: 승인 6건 + 2건 rejected_by="total_exposure"
```

**6건은 `int(예수금 ÷ (총평가 × 0.08))`과 정확히 같다.** 주문 1건당 8,049,947원,
예수금 50,308,183원 → 6건. `total_exposure_limit=1.0`은 사실상 "가진 현금 넘게
주문하지 마라"였고, 그 보장이 이 한 줄에 달려 있었다.

**섹터 한도 폐기는 그대로 유지된다** — 같은 섹터 6건(비중 0.48)은 수정 후에도 전부
통과한다. 이 수정이 되돌린 건 누적 판정이지 폐기한 룰이 아니다.

### 왜 지금 고쳤나 — 섹터 한도 폐기와 맞물린다

하루에 승인이 몰리는 상황은 **한 섹터가 달릴 때**다(후보가 상관돼 같이 통과한다).
그건 방금 섹터 한도를 없앤 바로 그 상황이라, 누적 버그가 실제로 발동할 확률이 가장
높은 시나리오에 다른 브레이크가 하나도 없게 됐다. 지금까지 안 터진 건 하루 최다
승인이 4건(8/12)이었고 전부 섹터가 달랐기 때문이지 설계가 막아서가 아니다.

돈이 새던 문제는 아니었다 — 초과 주문은 KIS가 현금 부족으로 거부하고
`execute_buy_order`는 성공한 매수에만 `cash_weight`를 차감하므로 장부도 안 깨진다.
실제 피해는 셋이었다:

1. **규칙 6이 깨진다.** 포트폴리오 단위 한도의 실질적 결정자가 브로커의 현금 체크였다.
2. **한도를 조이면 조용히 무력화된다.** `total_exposure_limit`을 0.8로 내려도 아무 일도
   안 일어난다 — 값만 바뀌고 판정은 그대로다.
3. **거부 사유 집계가 계속 빈다.** 한도 초과가 게이트 거부가 아니라 브로커 주문 거부로
   나타나서 CLAUDE.md 감시 지표에 안 잡힌다.

### 기존 테스트가 또 이 버그를 단언하고 있었다 (세 번째)

`test_recording_execute_fn_records_approved_buys_only`가 **"포트폴리오는 절대 안
바뀐다"**고 단언하며 정확히 이 버그를 지키고 있었다. 8/28 부분 체결 라벨, 오늘
노션 총정리 금액에 이어 세 번째다 — 이 프로젝트에서 **버그를 고칠 때는 그 버그를
단언하는 테스트가 있는지 먼저 볼 것.**

콜백을 `run_day`처럼 체인으로 부르도록 고치고 두 개를 더 붙였다:

- 5건 연속 승인 후 투자 비중이 실제로 0.40으로 쌓이는가
- 이 경로가 KIS를 **한 번도** 안 부르는가(`place_market_buy_order` /
  `fetch_account_balance` / `fetch_current_price`를 전부 예외로 막아두고 통과 확인),
  그리고 가상 포지션이라 `entry_price`가 None인가

### 수정 — 섹터 집중도 한도를 폐기했다 (정책 변경, 사용자 확정)

> "주식이라는게 한동안은 특정 섹터가 계속 오르는 경우가 있는데 그때 수익을

  + `RiskGateConfig`에 그 필드가 없다는 것도 따로 단언한다.

### 수정 — 매도 행에 실제 비용과 순손익을 남긴다

`realized_pnl_pct`는 그대로 둔다(마일스톤 3 IC는 가격 수익률로 봐야 한다). 그 옆에
비용을 뺀 값을 따로 붙였다.

- `kis.fetch_daily_fill_totals`가 `prsm_tlex_smtl`(추정제비용)까지 3-튜플로 돌려주고,
  `fill_between`이 주문 전후 차로 **이 주문 하나의 수수료**를 뽑는다. 수량·금액과
  똑같은 방식이라 같은 날 같은 종목 두 번 매도해도 안 섞인다.
- `FillRecord.fee: float | None`. **0.0으로 채우지 않는다** — "수수료가 0원"과
  "안 재봤다"가 같은 모양이 되면 순손익이 조용히 부풀어 오른다.
- `pipeline._trade_costs()`가 세 조각을 갈라 적는다:
  매도 수수료(**조회**) / 매도 거래세(**계산**, `kis.SELL_TAX_RATE`) /
  진입 시 수수료 중 이번 몫(**계산**, `kis.BROKERAGE_FEE_RATE`).
  `fee_source`가 `fill` / `estimated`(부분 체결분을 매도 수량으로 환산) /
  `computed`(체결 조회 실패)로 갈린다.
- 비용을 못 세우면 `net_pnl_amount`를 **None으로 둔다.** 0원으로 채우면 순손익이
  총손익과 같아지는데, 그게 지금 고치는 바로 그 상태다.
- 매수 행에도 `fee_amount`(조회값)를 남긴다 — 지금은 진입 수수료를 요율로 근사하는데,
  이 값이 쌓이면 나중에 일지끼리 맞춰 실제 값으로 되짚을 수 있다.
- 노션 매매일지에 `순손익률`·`순손익금액` 속성 추가 + 매도 행 본문에 "비용과 순손익"
  블록. **DB 스키마는 `setup_notion_workspace.py`를 EC2에서 돌려 반영했다** — 안 하면
  다음 매도 동기화가 400으로 통째로 실패한다(`_TRADE_JOURNAL_ADDED_PROPERTIES` 주석).

요율 두 개의 근거는 상수 주석에 있다. **`SELL_TAX_RATE = 0.0020`은 KIS 모의투자
기준이고 실계좌(2026년 코스피 0.15%)와 다르다 — 실거래 전환(규칙 7 해제) 시 반드시
다시 잰다.**

### 수정 — `day`를 UTC에서 KST로

`execute_open.py` / `check_stop_loss.py` / `decide_llm_sell.py` 셋 다
`datetime.now(timezone.utc)`로 `day`를 만들고 있었다. 그 `.date()`가 매매일지의 `day`와
보유기간 계산으로 그대로 들어간다. 09:01 KST = 00:01 UTC라 **지금까지는 1분 차이로
우연히 맞았다** — 크론을 09:00보다 조금이라도 앞당기면 그 순간 전 기록이 하루 밀린다
(832fb8b와 같은 버그). `decide_buys.py`는 이미 KST였다. 이제 다섯 진입점이 전부 같다.

### 특이사항 2 — 부분 체결인데 매매일지엔 `entry_price_source="fill"`로 남는다

488주 주문 중 12초 안에 95주(19.5%)만 잡힌 채 타임아웃됐고, 그 95주의 평균가

  300720 entry_price: 16233.684210526315 -> 16227.909 (-0.04%)

- **수량은 전부 일치했다.** 488주는 다 체결됐고, 체결 조회만 못 따라간 것이다.

문제는 값이 아니라 **라벨**이다. 매도 경로(`finalize_sell`)는 `fill.complete`를 보고
`fill_partial`로 구분해 남기는데, 매수 경로(`src/pipeline.py:325`)는 조건 없이

전체 체결 평균이고 어떤 게 앞부분 19%짜리인지 구분이 안 된다 —
`logs/cron.log`의 WARNING을 따로 대조해야만 알 수 있다.

코드 주석(`pipeline.py` 진입가 블록)은 이 위험을 이미 알고 있다:
"여러 단가로 나뉘어 체결된 주문의 앞부분만 보면 그 오차가 포지션 수명 내내 진입가에 남는다."
알면서 라벨을 안 남긴 셈이라, 나중에 진입가 품질을 되짚을 단서가 없다.

**고쳤다(같은 날).** 아래 "수정" 절 참고. `300720` 진입가 -0.04%는 교정하지 않고 뒀다
(`--apply` 미실행) — 손절선 기준 약 5원이라 교정 자체의 값어치보다 장중 상태 파일을
건드리는 위험이 크다.

### 수정 — 매수 경로에도 `fill_partial` 라벨을 붙였다

- `src/pipeline.py`: `entry_price_source = "fill" if fill is None or fill.complete else "fill_partial"`.
  **진입가 값 자체와 폴백 순서는 안 바꿨다** — 부분 체결 평균가도 호가보다 훨씬 나으므로
  그대로 쓰고, 근사치라는 사실만 라벨에 남긴다.
- `src/notion_sync.py`: `_entry_source_note()` 신설 + 매수 행에 "진입가 출처" 블록.

  전량 체결(`fill`)은 조용하다 — 정상 건마다 주석이 붙으면 진짜 근사치 건이 묻힌다.
  매도 행의 `_fill_source_note()`는 그대로 뒀다.

**기존 테스트가 이 버그를 그대로 단언하고 있었다.**

### 확인 — 매매일지 값의 출처 (조회값 vs 계산값)

섞여 있어서 정리해둔다.

**브로커 조회 원본 그대로**: `entry_price` / `exit_price`(= `fill.price`, 주문 전후
`tot_ccld_amt` 차 ÷ `tot_ccld_qty` 차), `sell_amount`(전량 체결 시 `fill.amount`),
`shares_before` / `shares_after`.

**코드가 계산**: `realized_pnl_pct`(= (청산가-진입가)/진입가), `holding_days`,
`position_fraction_sold/remaining`, `portfolio_weight_*`, 그리고 부분 체결일 때의
`sell_amount`(= 관측 평균단가 × 실제 매도 수량, `sell_amount_source="estimated"`).

**호가 근사(최후 수단)**: 체결 조회가 전부 실패한 경우에만. `*_source` 필드가
`quote_fallback`으로 남는다.

즉 **가격과 금액은 실조회, 비율과 기간은 계산**이다. 계산의 입력이 되는 진입가가
상태 파일 값이라, 그게 어긋나면 실현손익률이 통째로 틀어진다 — 2026-08-15 192820
오익절(호가 210,000이 진입가로 남아 실제 +6.6%를 +20%로 오판)이 정확히 그 사고였고,
`reconcile_portfolio.py`가 그래서 있다.

### 수정 — 추가매수 시 진입가를 **주식수 가중**으로 고쳤다 (발견 직후 같은 날)

`src/pipeline.py` 추가매수 분기(`existing is not None`):

```python
old_basis = (existing.entry_price or entry_price) * existing.weight
new_basis = entry_price * trade_weight
existing.entry_price = (old_basis + new_basis) / (existing.weight + trade_weight)
```

`weight`는 **매수 시점 원가 기준 비중**이다(`src/reconcile.py` docstring이 명시).
즉 `weight ∝ 수량 × 단가`(원가)라, 위 식은 단가를 원가로 가중한 평균 —
결과적으로 **단가의 제곱으로 가중**된다. 올바른 평균 원가는 주식수 가중이다.
바로 아래 줄에서 `existing.quantity`는 정확히 더하고 있어 수량은 멀쩡하다.

실제 코드 경로로 재현(100주 @1,000원 보유 → 2,000원에 50주 추가매수):

```
보유수량      : 150주  (100 + 50)
기록된 진입가 : 1,500.00원
올바른 진입가 : 1,333.33원   ((100x1000 + 50x2000) / 150)
오차          : +12.50%
```

진입가가 부풀면 **손절은 일찍, 익절은 늦게** 발동한다. 2026-08-15 192820 오익절
(호가가 진입가로 남아 실제 +6.6%를 +20%로 오판)과 같은 부류의 사고다.

**죽은 코드가 아니다.** `position_limit`이 0.15인데 진입은 0.08씩이라 온전한 포지션은
0.08+0.08=0.16 > 0.15로 게이트가 막지만, **부분 익절로 비중이 줄어든 종목은 뚫린다.**
후보 유니버스에서 보유 종목을 빼지도 않는다. 지금 `192820`이 비중 0.0118이라
0.0118+0.08=0.0918 < 0.15 — **현재 유일하게 노출된 포지션이고, 하필 트림 이력이
가장 많은 종목이다.**

**수정 내용**: 양쪽 수량이 다 있으면 `(old_price*old_qty + new_price*new_qty) /
(old_qty+new_qty)`, 수량을 안 들고 있는 경로(시뮬레이션)에서만 기존 비중 식으로
물러선다. 브로커 매입평균가가 애초에 주식수 가중이라 이 식이 그것과 일치한다.
`entry_day` `exit_plan` `take_profit_stage`는 추가매수에서 안 건드리는 기존 동작
그대로 뒀다(CLAUDE.md: 물타기하며 손절선을 넓히는 경로를 열지 않는다).

기존 테스트 `test_adds_to_existing_position_with_weighted_average_entry_price`는
`quantity` 없는 포지션이라 폴백 경로를 타고 있었다 — 이름을
`..._falls_back_to_weight_when_shares_unknown`으로 바꿔 그 사실을 드러내고,
주식수 가중을 확인하는 테스트를 따로 추가했다(트림돼 비중 0.02인 포지션 기준).

| score 부호 | +5 / −9 / 동점 16 (평균 −0.015) | **+16 / −4 / 동점 10 (평균 +0.033)** |
| confidence 부호 | +7 / −8 / 동점 15 (평균 −0.005) | +13 / −10 / 동점 7 (평균 +0.003) |

부호검정 양측 **p=0.012**. 크기(0.033)는 잡음의 절대평균(0.038)과 비슷해 **콜 하나만
보면 구분이 안 되지만, 방향이 쏠려 있다.** 세 분석가가 전부 같은 방향이다 —
차트 +0.038(6↑/1↓), 뉴스 +0.030(4↑/0↓), 공시 +0.030(6↑/3↓). 한 분석가가 끌고 간 게 아니다.
confidence는 영향 없음(+0.003), 점수 부호가 뒤집힌 건 0건.

**즉 `reasoning`을 빼면 분석가가 체계적으로 강세 쪽으로 +0.03 치우친다.** 근거를 대라는
요구가 채점을 규율하고 있었다는 뜻이다 — 버려지는 필드인데도 값을 만드는 과정이 일을 하고 있었다.

**이 방향이 이 프로젝트에서 가장 나쁜 방향이라 기각한다.** 잡음은 표본이 쌓이면
