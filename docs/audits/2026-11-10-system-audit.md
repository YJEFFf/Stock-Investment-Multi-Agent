# 전체 시스템 감사 — 2026-11-10

## 결론과 범위

**숨은 결함이 있다. 정상 응답·테스트 통과·서비스 실행 중이라는 사실만으로 입력의
최신성, 체결 수량, 복구 가능성까지 보장되지는 않는다.** 현재 가상 청산의 시세와 감시
경로부터 보완하고, 정지된 매매 경로의 장부·복구 문제는 신규 계좌 재개 전에 해결해야 한다.

이번 감사에서 운영 코드·설정·장부를 수정하거나 배포하지 않았다. `EXIT_ONLY=True`, 기존
보유분의 동결 ExitPlan, 보존 포트폴리오·매매일지와 가상 장부를 유지했다. 거래소·증권사에
주문, 잔고 조회, 시세 시험 호출을 하지 않았고 모델·외부 알림도 호출하지 않았다.
서버는 읽기 전용으로 확인했으며 공개 문서 조회와 앱의 비인증 GET 건강 검사를 수행했다.

- 범위: 수집 → 정량 필터 → 분석가 → 토론·매니저 → 게이트 → 주문 → 장부·복구 →

## 현재 가상 청산과 감시

### F01 — 당일이라는 이유만으로 오래된 스냅샷을 수용

위치: [collectors.py](../../src/collectors.py) `fetch_naver_quotes`(916행),
[kis.py](../../src/kis.py) `Quote`(419행), [exit_only.py](../../src/exit_only.py)
`valid_quote/monitor`(205·213행).

네이버 응답의 `localTradedAt`은 날짜 비교에만 쓰이고 `Quote`로 전달될 때 사라진다.
현재 소비자는 가격·고저가의 수치 관계를 확인하지만 공급자 체결 시각이나 응답 스냅샷의
신선도를 확인하지 못한다. 새 `observed_at`은 조회 시각이다.

`stale_naver`에서 09:01의 OPEN 응답을 14:00에 다시 제공했다. 보유분 9주의 가상 매도가
발생했고 시세 확인 시각은 14:00으로 저장됐다. **공급자가 오전 응답을 재전달하는 장애를
소비자가 구별하지 못한다.** 실제 거래가 드문 종목의 마지막 체결 시각이 오래된 경우까지
모두 오류라고 단정하는 것은 아니다. 이 둘을 구별할 공급자 시각·거래 상태·수신 시각이 필요하다.

현재 기록에서 이 장애로 잘못 팔린 건을 확인한 것은 아니다. KIS 응답도 `Quote`에 공급자
시각을 보존하지 않아 같은 신선도 계약이 필요하다. 수정 시 출처별 시간 필드를 보존하고,
검증하지 못한 가격은 판단 불가로 남겨야 한다. 단순히 조회 성공 시각을 최신 가격의 증거로
사용해서는 안 된다. 신선도 허용 범위는 데이터 특성을 확인해 정해야 한다.

### F02 — 장후 네이버 종가 평가가 막힘

`fetch_naver_quotes`는 `marketStatus == OPEN`일 때만 고저가를 보존한다. CLOSE이면
오늘 15:30의 정상 종가여도 고저가가 `None`이 되고, 가상 장부의 `valid_quote`는 이를 거부한다.
`closed_naver`에서 유효한 종가 110을 줬지만 15:35 평가가 이전 값 100으로 남고 미조회로 표시됐다.

KIS 성공 시에는 드러나지 않는다. 장중 매도 가능한 가격인지와 장후 평가에 쓸 종가인지를
별도 검증해야 한다. 장후 종가를 수용해도 장후 가상 매도를 허용하는 것은 아니다.

### F03 — 감시가 멈췄는데 겉보기에는 정상일 수 있음

위치: [exit_only.py](../../src/exit_only.py) `monitor`,
[monitor_exit_only.sh](../../scripts/monitor_exit_only.sh),
[mobile_data.py](../../src/mobile_data.py) `exit_only_snapshot`(254행),
[recover_services.py](../../deploy/recover_services.py) `tick`.

세 가지가 연결돼 있다.

1. KIS 시세 스레드를 모으는 `gather`에 전체 회차 기한이 없고 실행 셸에도 `timeout`이 없다.
   한 호출이 반환하지 않으면 장부 잠금이 유지된다. `blocked_monitor`에서 첫 호출을 멈추고
   다음 분의 논리시각으로 호출하자 후속 회차는 잠금 때문에 검사 없이 반환했다. 이 재현은
   실제 서버를 멈춘 실험이 아니며, 운영에서 무한 정체를 관측했다는 뜻도 아니다.
2. 앱의 감시 지연 경고는 거래일 09:02–15:36에만 나온다. 전날 16:00 이후 멈춘 장부를
   다음 날 20:00에 조회한 `stale_evening`에서는 `status=exit_only`, `warnings=[]`였다.
   오래된 날짜는 화면에 남지만 당일 감시 누락에 대한 경고가 사라진다.
3. `exit_only_snapshot`이 기존 `warnings`를 비운다. `hidden_corrupt_history`에서 손상된
   매매일지 행을 독자가 감지했지만 최종 응답에서는 경고가 사라졌다. 과거 거래 목록이
   여전히 화면에 표시되므로 과거 자료 손상 경고까지 지우는 것은 부적절하다.

서비스 복구기는 프로세스 활성 상태와 HTTP 건강 응답을 주로 확인한다. cron이 살아 있고
`/healthz`가 200이어도 위 감시 작업이 완료된다는 보장은 없다. 완료 시각을 별도로 감시하고,
회차 전체 종료 기한, 실패 기록·알림, 장후에도 유지되는 미해결 경고가 필요하다.

### F04 — 거래 달력과 시간 정책이 분리돼 있음

위치: [market_calendar.py](../../src/market_calendar.py), [crontab](../../deploy/crontab),
`exit_only.monitor/apply_quotes`, `mobile_data.exit_only_snapshot`, `deploy/pull.sh`.

- 달력은 2026년만 지원한다. `next_year`에서 잔여 보유분이 있는 상태로 2027-01-04 앱
  스냅샷을 만들면 처리되지 않은 `ValueError`가 발생한다. 알 수 없는 연도에 거래를 막는

- 배포기는 갱신 전 운영 코드의 달력으로 날짜를 검사한다. 2027년 평일에 들어서면 새 달력

  달력 미지원 시 사용할 명시적인 유지보수 절차가 필요하다.

  운영 기록의 대상 기간 이전이므로 이 누락으로 실제 주문이 나갔다고 주장하지 않는다.

  [유가증권시장 공시 원문 재게시](https://stock.mk.co.kr/news/disclosure/template/1028611).

  올해 정확한 변경 시각은 배포 전 원문으로 최종 확인해야 한다. 파생상품 시간 변경은

권고: 거래일·개장·마감·종가 평가·배포 제한을 한 날짜별 세션 정의에서 계산한다.

### F05 — 필수 종목 뉴스 수집 실패가 정상 게이트를 통과

위치: [pipeline.py](../../src/pipeline.py) `make_news_analyst_fn`(679행),
[judgment.py](../../src/judgment.py) `judge`, [run_history.py](../../src/run_history.py),
[decide_buys.py](../../scripts/decide_buys.py).

종목 뉴스가 `None`이어도 업종 뉴스만 있으면 `company_news=[]`로 바꿔 분석가를 호출한다.
실행 이력에는 필수 수집 실패가 남지만, `Decision.degraded`는 반환된 의견 개수로 판단한다.
차트·뉴스·공시 의견이 모두 생기면 완전한 분석으로 취급할 수 있다.

`partial_news`는 종목 뉴스 실패와 업종 뉴스 성공을 주입했다. 결과는
`required_source_failed=True`, `decision_degraded=False`, `gate_approved=True`였다.
모델의 높은 점수는 고정 시험 응답이다. 실제 모델이 반드시 그렇게 답한다는 뜻은 아니며,
프롬프트의 “신뢰도를 낮춰라”에 데이터 장애 통제를 맡기고 있다는 점을 증명한다.

필수 자료의 상태를 종목별 결정·게이트까지 전달해야 한다. `None`과 정상적인 빈 목록을
구분하고, 종목 뉴스가 실패했을 때 업종 의견이 그 실패를 지우지 못하게 해야 한다.
실제 보존된 403개 뉴스 입력에서는 업종 뉴스만 있는 사례가 없었다.

### F06 — 업종을 모르면 모든 기사가 업종 뉴스가 됨

위치: [collectors.py](../../src/collectors.py) `fetch_sector_news`(661행),
[pipeline.py](../../src/pipeline.py) `build_universe_with_sectors`.

업종 매핑을 못 구하면 빈 문자열이 사용된다. 뉴스 필터의 `sector in title`에서 빈 문자열은
모든 제목에 일치한다. `empty_sector`에서 무관한 기사가 해당 종목의 업종 뉴스로 전달됐다.

실행 이력에 10월 6·7·8·12·13·14·15·16·19·20일의 `sector_map failed`가 있다.
선택 자료로 분류돼 실행은 completed로 남았다. 당시 정확한 뉴스 입력이 보존되지 않아
그 10일 모두에서 무관한 기사가 실제 투입됐다고 확정할 수는 없다.

### F07 — 실제 뉴스 입력과 기준 시각이 다름

위치: `make_news_analyst_fn`의 `NewsContext(as_of=day)`, `news_analyst`.

최대 차이는 **2,814.64초, 약 46분 55초**이며 이 중 게이트 승인 결정은 1건이다.
전체 실행 시작 시각을 재사용하는 동안 뒤에 수집한 종목에 새 기사가 유입될 수 있다.
실시간 미래 정보 취득의 증거가 아니라, 기록된 자료 기준 시각이 부정확하다는 증거다.

항상 버려야 한다는 결론도 아니다. “최근 뉴스”와 과거 배경을 구분할 기준이 빠진 상태다.

실행 시각, 수집 완료 시각, 기사 발표 시각, 분석 기준 시각을 분리하고 입력을 그대로
보존한다. 시점 고정이 필요하면 수집 전에 cutoff를 정해 이후 기사를 제외한다. 기사 보존
기간은 별도로 결정하고, 신규 기사 없음과 수집 실패는 다르게 표현한다.

수정주가를 분석에 쓰는 것, 실제 보유 수량·원가를 조정하는 것, 배당 등 총수익을 계산하는

해결해서는 안 된다. 기업행동을 검증하지 못하면 해당 자료의 비교 가능성을 미확인으로 남긴다.

### F10 — 접수 번호가 있으면 미체결 수량까지 반영

미확인 주문 마커와 경보는 남아 중복 주문을 막는다. 하지만 이것이 수량의 정확성을 보장하지는
않는다. 후속 복구는 원래 주문량의 완전체결을 확인하는 경로여서 영구적인 일부 체결·잔량 취소를
해결하지 못한다. 주문량·접수량·확정 체결량·미체결 잔량을 분리하고 관측한 체결만 장부에
반영해야 한다. 취소/만료의 최종 상태까지 확인하는 계약이 필요하다.

### F11 — 체결은 끝났지만 저장 전 중단되면 복구에서 제외

확정 체결 뒤의 저장 완료 상태를 재실행 가능하게 만들어야 한다. ready 주문에 대해 일지·

매니저 프롬프트는 자신이 손절·익절 비중·트레일링을 결정해 동결한다고 설명하고, 현재 폐기된
섹터 집중도·일일 손실 게이트도 존재한다고 설명한다. 실제 출구 규칙은 코드가 변동성으로
정하고 모델의 출구 숫자는 비교 기록용이다. 현재 주문 기준이 모델에 의해 바뀌는 것은 아니지만
모델이 가정한 안전장치와 실제 승인 계약이 어긋난다. 프롬프트 수정은 버전과 평가 구간을 남겨야 한다.

정지된 개발용 `scripts/run_daily.py`는 현행 실행 잠금·일일 실행 이력 경로를 통하지 않고,
LLM 매도 함수를 직접 전달한다. `EXIT_ONLY`가 지금은 차단하지만 재개 때 잘못 사용하면
기존 분리 스케줄의 보호를 우회할 수 있다. 노션 리포트 호출도 현재 함수가 받지 않는
`total_value=` 인자를 전달해 실패한다. 이 진입점을 폐기하거나 명시적인 모의 개발 환경에서만
실행되도록 제한하는 편이 안전하다.

1. **현재 추적 보호:** F01–F03의 공급자 시각, 종가 평가, 회차 기한, 완료 감시·경고 보존을

2. **달력과 기업행동:** 특별 거래일 운영시간을 공식 공지로 확인해 공통 세션 정의에 반영한다.

## 새 공시가 없는 날의 자료 사용

현재 `EXIT_ONLY`에서는 매일 분석 자체를 하지 않는다. 재개 시 현행 분석 경로는 종목마다
분석일을 포함한 최근 30일(KST 달력일)의 최종 공시 목록을 조회한다. 새 공시가 없어도 그
기간 안의 기존 공시가 있으면 같은 공시가 다음 날 분석에 다시 들어갈 수 있다. 해당 기간에
공시가 전혀 없으면 공시 의견은 `None`이며, 조회 실패도 정상적인 ‘공시 없음’과 구분해 기록한다.
현재 공시 분석에는 제목·제출인·접수일·접수번호·비고가 들어가고 공시 본문·재무 수치는 들어가지
않는다. 앞선 공시 수정은 이 범위의 누락·잘못된 매핑·페이지 처리·날짜 표기를 보완한 것이다.
같은 자료를 새 관측일에 다시 봤다는 사실과 새 공시가 발생했다는 사실은 구분해야 한다.
